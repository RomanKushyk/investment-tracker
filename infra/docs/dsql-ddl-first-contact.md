## The question, and the answer

**`USING btree` is REJECTED**, with and without `ASYNC`:

```
CREATE INDEX       "probe_a" ON "btree_probe" USING btree ("user_id","created_at")
CREATE INDEX ASYNC "probe_b" ON "btree_probe" USING btree ("user_id","created_at")
  -> 0A000  USING not supported for CREATE INDEX
```

A control ran in the same connection so the failure could not be blamed on the
harness, the table or the columns:

```
CREATE INDEX ASYNC "probe_c" ON "btree_probe" ("user_id","created_at")   -> job_id
```

**`ASYNC` is mandatory on its own**, asked separately in round 2 because
round 1's `probe_a` carried `USING btree` too and died on that first — the
error masked the answer, and one statement testing two things answers neither:

```
CREATE INDEX       "i_plain" ON "t" ("a","b")  -> 0A000  unsupported mode. please use CREATE INDEX ASYNC.
CREATE INDEX ASYNC "i_async" ON "t" ("a","b")  -> job_id
```

## The reason is not the one the grammar suggested

The documented grammar omits the `USING` clause entirely, which reads as "DSQL
has no `USING`". It is not that. **`USING` is accepted — with DSQL's own access
method name:**

```
CREATE INDEX ASYNC "probe_d" ON "btree_probe" USING btree_index ("user_id","created_at")  -> job_id
```

And `btree` is not a missing name either. `pg_am` holds all nine of
`brin, btree, btree_index, btree_table, gin, gist, hash, heap, spgist`. So
`btree` exists as a catalog row and is still refused as an index method: the
rejection is a whitelist of one, not an unknown identifier. **Predicting this
from the docs would have got the outcome right and the cause wrong** — which is
why it was run rather than reasoned.

`pg_get_indexdef` prints every index back in the `btree_index` form, the
primary keys included:

```
CREATE UNIQUE INDEX account_user_id_id_pk ON probe_20260827.account
  USING btree_index (user_id, id) INCLUDE (provider, name, created_at)
CREATE UNIQUE INDEX btree_probe_pkey ON probe_20260827.btree_probe
  USING btree_index (id) INCLUDE (user_id, created_at)
CREATE INDEX asset_user_created ON probe2_20260827.asset
  USING btree_index (user_id, created_at)
```

The `INCLUDE` on the primary key is DSQL's own doing — nothing in
`../schema/user.ts` or in the probe table asks for it, and in **both** primary
keys read back it covers exactly the columns the key does not: `account`'s
three of five, `btree_probe`'s two of three.

**Two tables is not "every table", and this file will not say it is.** That the
primary key carries all remaining columns is the index-organized storage
`../../docs/superpowers/specs/data-model/price-archive.md` describes for the
archive tables — so the general form is documentation plus two consistent
observations, not a measurement of the general form. `asset` has 17 columns and
its primary key was never read back. On a page whose whole point is that
reasoning from documentation got the *cause* wrong, generalizing from two
tables would be the same move in the other direction.

## So promotion is TWO transformations, not one

The drafts README described one — `CREATE INDEX` → `CREATE INDEX ASYNC`. That
alone produces a statement DSQL refuses. The generated line, and what must
actually be sent:

```sql
-- generated by drizzle-kit, verbatim in 003_user_schema.sql
CREATE INDEX "asset_user_created" ON "asset" USING btree ("user_id","created_at");
-- what DSQL accepts
CREATE INDEX ASYNC "asset_user_created" ON "asset" ("user_id","created_at");
```

`USING btree_index` would also be accepted, and is the wrong choice: it is a
DSQL-only spelling that would make the promoted file un-runnable against the
PGlite Postgres `../src/user-schema.test.ts` uses, for no gain over omitting
the clause.

## Accepted is not built

Round 1 tried to confirm the builds with `SELECT sys.wait_for_job(…)` and got
`42809 sys.wait_for_job(unknown) is a procedure`. Both index jobs were
therefore last seen `submitted`, with `indisvalid = false`, and round 1 could
not honestly claim more than that the DDL parsed. **It is a `CALL`:**

```
CALL sys.wait_for_job('koekm6psfrerxngerjvtoxlvnu')  -> succeeded = true
SELECT status FROM sys.jobs WHERE job_id = '…'       -> completed
```

Both real indexes then read `indisvalid = true`. A migration runner that fires
`CREATE INDEX ASYNC` and moves on has not created an index; the docs' own
failure mode is a job that ends `failed` leaving the definition behind
`INVALID`, which AWS says it does not clean up. Nothing here made a job fail,
so the recovery — a hand `DROP INDEX` — is documentation, not measurement.

## The whole file applies

All seven statements of `003_user_schema.sql`, verbatim except the two index
lines, ran clean: <!--f:userSchema.tables-->5<!--/f--> tables with one primary
key each, <!--f:userSchema.compositeKeys-->4<!--/f--> of them composite
(`app_user` keys on `user_id` alone), named `CONSTRAINT`s throughout,
<!--f:userSchema.uniques-->3<!--/f--> `UNIQUE`s,
<!--f:userSchema.checks-->23<!--/f--> `CHECK`s, one `DEFAULT 0`, and the types
`uuid`, `text`, `numeric` (unqualified), `smallint`, `bigint`, `date`,
`timestamptz`.

Those four counts are fenced, not typed. The first draft of this page said
"sixteen `CHECK`s, two `UNIQUE`s, five composite primary keys" — three wrong
numbers, each repeated in three files — and `src/facts/` exists for exactly
that. They derive from the DDL itself, so the next schema change corrects them
here without anyone remembering to.

**And the constraints are enforced, not merely accepted** — the drafts README
noted that `CHECK`, `UNIQUE` and `DEFAULT` had no precedent against the real
cluster:

| Attempted | Result |
|---|---|
| `status = 'bogus'`, `decided_ck` deliberately satisfied | `23514` — `app_user_status_ck` |
| `role = 'root'` | `23514` — `app_user_role_ck` |
| `status = 'pending'` with `decided_at` set | `23514` — `app_user_decided_ck` |
| a second row with an existing `email` | `23505` — `app_user_email_uq` |
| a row omitting `data_version` | `DEFAULT 0` landed |

Round 1's status-CHECK row was also missing `decided_at`, so `decided_ck` fired
first and `status_ck` was never reached — the row proved a constraint, just not
the one it was named after. Round 2 set `decided_at` so the intended constraint
was the only one it could violate.

## DSQL has foreign keys now, and the README said it does not

The drafts README stated as fact that "`REFERENCES` is absent from the
grammar" — corrected in the same branch as this file. AWS now documents
`FOREIGN KEY`, referential actions and deferrability, so it was measured —
**composite**, because the tables an FK here would link are keyed
`(user_id, id)`, so every reference among them carries two columns:

```sql
CONSTRAINT "child_parent_fk" FOREIGN KEY ("user_id","parent_id")
  REFERENCES "parent" ("user_id","id") ON DELETE RESTRICT
```

Accepted, and enforced in both directions: a child row pointing at nothing gave
`23503`, and deleting a referenced parent gave `23503` naming the child table.
`pg_get_constraintdef` reads it back unchanged.

**Whether this schema should use them was not decided here** — it was filed as
`../../docs/plans/PLAN-OPEN.md` O34 and **ruled on 2026-08-28 (D101): W7 ships
none.** The grounds were that it removes the nightly integrity audit
`../../docs/superpowers/specs/data-model/ledger.md` specifies, that cascade
behaviour interacts with DSQL's 3,000-row transaction limit, and that a key can
be added later anyway (D100). Adoption is now **O33**'s to decide.

## Reproduce

Three one-off scripts, not committed: they connect with `DsqlSigner` exactly as
`../src/capture.ts` does, read `003_user_schema.sql` off disk, and drop their
schema in a `finally`. Anything re-run against the cluster should keep both
properties — a throwaway schema and an unconditional teardown — because the
alternative is a half-created user schema in `public` that the next promotion
walks into.
