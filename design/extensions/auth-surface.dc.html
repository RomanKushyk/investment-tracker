The signed-out surface — entry, sign-in, the application, the four answers, the first sign-in

Drawn from brief #164. Sign-in is the entry and the application is one link away; the shell is a top bar with no sidebar; the ceremony is identifier-first because Cognito offers a passkey only to a named account; Google's button keeps Google's colours. Ukrainian in every frame but one, as the app defaults.

T1 · The shell and the entry

A page with no portfolio behind it — signed out, a refused caller, the first sign-in — mounts NEITHER signed-in shell. It gets a top bar — the 5h mark and «quirenote» on the left, the shipped language control (src/screens/Settings.tsx:159-193) on the right at its own 206 × 38 — and one card, top-anchored 64 below the bar at ≥ md and 16 below it at 360, so the card's top edge never moves between steps. A step still REPLACES what lies under the pointer. On the common path — every account before its first passkey — the password step's «Увійти» takes exactly the rect of the just-pressed «Продовжити» at 1280 and overlaps it at 360, and the passkey step puts «Увійти з паролем» across it at 360. So a pressed submit turns busy and takes no second press until the next step is up (S2 §3, loading), and an empty password that gets through anyway is refused by a sentence, «Вкажіть пароль.», never greyed. The bar's instance drops the max-sm:w-full stretch the /settings one carries (Settings.tsx:169): there it fills a card row, here it would push the lockup off a 360 bar. The entry is sign-in: the address, «Продовжити», the Google button under an «або» rule, and the application one link away. Google is conditional: the provider exists only when GoogleSignIn is enabled (infra/template-user.yaml:79), and without it neither the rule nor the button renders — the card runs from «Продовжити» straight to the link, which keeps the 22 above it that it has everywhere. The last frame is English, with the address field focused.

T2 · Sign in, step by step

Identifier-first, because this pool cannot do otherwise: Cognito issues no passkey challenge without a username, so the browser's passkey autofill has nothing to offer before the address is known. «Продовжити» sends the address with PREFERRED_CHALLENGE=WEB_AUTHN: an account with a passkey is answered with the passkey challenge, which opens the OS sheet at once — the card behind it says so. An account without one is answered SELECT_CHALLENGE with AvailableChallenges: ["PASSWORD_SRP", "PASSWORD"] and no WEB_AUTHN (docs/reference/COGNITO-POOL-PARAMS.md:229-235; AWS: "If you didn't submit a preferred challenge or the submitted user isn't eligible for their preferred challenge, Amazon Cognito returns a list of options in AvailableChallenges"), and the app answers with a password challenge — over SRP, as #165 names it: the password step. An address with no account is answered too: "Amazon Cognito responds to requests for choice-based authentication with a random selection from the challenge types allowed for the user pool" (Cognito developer guide, Managing user existence error responses), and this pool allows PASSWORD and WEB_AUTHN. So the passkey sheet can open for an address that has none; the not-finished state is true for it as written, since that device has no passkey for that address. Whether the random answer tells a real address from an invented one across two submissions is not settled here — #165 probes the dev pool before building on it. The address stays on screen with «Змінити». A cancelled sheet names the two common causes of a NotAllowedError — which WebAuthn calls "a catch-all", and which the page cannot tell apart — in one sentence under «Увійти з паролем» with role="alert" and «Спробувати ще раз» as a link beneath it: the passkey step stays exactly as it was, so the OS dialog's closing moves nothing on the card (T6). No refusal sentence moves its button: the line under every field is reserved, empty or not, and a sentence about the whole step sits BELOW its button, with role="alert" — «Неправильна адреса або пароль.» among them, because it blames neither field and so turns no border. A field's own refusal is its input's aria-invalid="true" and aria-describedby the reserved line, and focus moves to the first refused field.

T3 · Apply for access

One field, in the same card and at the same top edge, reached from the entry's foot and linking back. The answer is a constant 202 whatever became of the address, and nothing is mailed on submission — so the recorded view says recorded, promises no status, and names the one email the application can bring: the invitation, if it is approved. The 429 is the route's own throttle, counted for everybody, so it names no device and no wait longer than a moment.

T4 · The four answers

What a SIGNED-IN caller meets when the first authenticated request answers 403. Each carries «Вийти» and none offers «Увійти»: a sign-in would succeed and change nothing. A lucide glyph in muted tells the four apart without colour; none takes neg, because none is a mistake the reader made. forbidden shows no address and no reason — its causes must not be told apart. no application's two buttons are stacked at both widths, where the brief asked for them side by side at ≥ md: side by side, each is (384 − 10) / 2 = 187 wide and holds 187 − 40 − 3 = 144 of content against a 147,5 label («Вийти й подати заявку»). T5 · The first sign-in

Between an invitation and a passkey, in #44's order. The invitation's temporary password answers NEW_PASSWORD_REQUIRED: one field, the show toggle, and the pool's own rule under it — muted as a hint, so nobody meets the rule first as an error. Refused, the same sentence turns neg AND takes lucide's circle-alert and role="alert": the sentence was already on screen, so colour alone would be the whole change, which WCAG 1.4.1 does not accept (Interaction rules). An alert whose text does not change is generally not announced (MDN, the alert role), so #165 re-inserts the sentence on each refusal, and the input carries aria-invalid with the line as its description. The form keeps the address as a display:none email input, the implicit account Chromium asks a password form to carry, so a password manager can save the new password against it. Every form's primary is a type="submit" button, since with that second input Enter submits the form only through one (the sheet's forms are method="dialog", so they submit nowhere). Then the passkey, offered once the access token exists: FIDO's mark on the button in the button's own colour, «Не зараз» under it because a device may have no authenticator. Not created keeps the offer exactly as it was — «Створити ключ доступу» still creates — and says what happened in one sentence under «Не зараз», with role="alert", so the OS dialog's closing moves nothing (T6).

Google’s branding guidelines fix the button’s fill, stroke and label per theme and require the standard-colour G, "to complete the app verification process". The palette has no name for any of them, so they are minted rather than approximated; #165 adds them to @theme in both themes. T8 · Refused, and not drawn

  • One email box for sign-in and application — it would branch on whether the address has an account, and say so to anybody typing one; the constant 202 exists to prevent that.
  • Passkey autofill (autocomplete="username webauthn", conditional mediation) — Cognito issues no challenge before a username; the token does nothing without one.
  • A refusal sentence that pushes its button down — the line under every field is reserved and a sentence about the whole step sits below its button, so the pointer that just pressed it is still on it.
  • A vertically centred card — any change of its height, a refusal sentence below the button included, would shift the button it sits above.
  • Flags on the language control, or a list of links — the /settings control, each language in its own name.
  • A theme control on the bar — the stored setting holds, system by default.
  • neg on rejected or forbidden — neither is an error the reader made.
  • A password confirmation field — the show toggle catches the typo a second field was for.
  • «Забули пароль?» — NOT DRAWN, not refused: no issue owns the recovery screens, and a link to nothing is worse than none. It needs a brief.
