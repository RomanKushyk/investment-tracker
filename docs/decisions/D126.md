## D126 — A backup is a mirror, not a door (2026-09-01)

[`D125`](D125.md) put the unit-count requirement on three doors. Two of them
were right. The third deadlocked the owner's real data, and the seventh
pre-merge review is what found it.

## The deadlock, in the order it bites

A store created before this branch holds pre-#31 `buy` / `reinvest` rows with no
`quantity`. Nothing backfills them and nothing can —
`w7-migration-translations.md` §4 calls those counts unrecoverable.

| the owner tries | what happened under D125 |
| --- | --- |
| Settings → Download backup | refused: the export re-reads its own output |
| Import a backup | refused: the pre-import safety backup is that same export, and `ImportDialog` returns without importing when it fails |
| Danger zone → wipe | the "Download backup first" CTA cannot produce a file |
| Fix the rows instead | **there is no control** — `useUpdateTransaction` has no caller in `src/`; the ledger offers delete only |

Three ways out of one door, and none of them open. The failure message even
named the Transactions screen as the remedy, which is a screen with no edit
affordance on it.

## The rule that survives the correction

**A backup's job is to carry what the store legitimately holds.** A door decides
what may ENTER the system; a mirror records what is already in it. Putting an
entry rule on the mirror does not stop bad data being created — the form and the
coupon card already do that — it stops good data being SAVED.

So the requirement stays exactly where data is created and where it migrates:

- `transactionSchema` — [`D124`](D124.md), unchanged.
- The S5 coupon card's own units field — D125, unchanged.
- `transaction_quantity_required_ck` — D125, unchanged. Its argument was always
  about SEQUENCING (the W7 backfill runs before that table takes the owner's
  history), and a migration that has not happened cannot be deadlocked by it.

## Version back to 3

D122's rule cuts both ways: **the version tracks what a build ACCEPTS.** 4 was
bumped for a stricter reader; the stricter reader is gone, so the break has no
reason left, and a version carrying a reason that no longer exists is worse than
no bump. Nothing ever shipped 4 — it lived only on this unmerged branch — so
walking it back costs no file on anyone's disk. That is precisely why it is
walked back rather than kept for tidiness.

## The export guard stays

`useBackupDownload` still parses what `buildBackup` produced and refuses to
offer a file that comes back rejected. It is what turned "the owner discovers an
unrestorable file at the one moment it mattered" into a refusal at the moment of
writing — which is how this deadlock became visible at all, rather than shipping.

It should now never fire, so it reports the parser's own first issue instead of
guessing at a cause, and it honours `quiet` like the `catch` beside it: the
pre-import safety backup reports its own failure in its own words.

**The invariant is `never write what you cannot read`**, and it outlives
whichever rule breaks it next. `json.test.ts` pins the round trip — a legacy
count-less row survives build → parse — so the guard reads as necessary rather
than defensive.

## Supersedes

D125's backup-importer rule, its `units-missing-on-position-row` issue code and
its version literal. Everything else in D125 stands, including the seed's seven
counts: those were never about the importer, and without them a NEW profile
would still export a file it could not read back.
