## D129 — The asset is a question only some rows answer (2026-09-02)

The owner reported that a deposit could not be entered correctly: the «Актив»
field should hide on that type and should not stand in the way of the submit.

### What was actually wrong

Two classes of row have existed in this domain since P1. `core/types.ts` says
so on the field itself — `assetId: string; // '' for portfolio-level rows
(deposit)` — and four other places already act on it:

| Place | What it already did |
| --- | --- |
| `lib/seed.ts` | writes `assetId: ''` on all three demo deposits |
| `core/backup/json.ts` | `if (tx.assetId !== '' && !assetIds.has(...))` — exempts `''` from the referential check |
| `core/derive.ts` | `portfolioXirr` reads only the type; its comment calls a deposit's assetId *noise* |
| `TransactionPanel.tsx` | the ledger row renders `asset ? shortLabel(asset) : t.transaction.portfolioRow` — «Портфель» |

The form was the one door that could not produce that shape. `assetId:
z.string().min(1)` asked a single question of all nine types, so:

- with assets present, every deposit typed in borrowed whichever asset the
  select happened to be showing, and the ledger read «Внесок · REIT»;
- with no assets present, the field could not be satisfied at all — and a
  deposit is the first transaction anyone records, before there is anything to
  buy.

The second is the "неможливо" in the report. The first is the "коректно".

### Why the two halves are shaped differently

[`D124`](D124.md) enforces the unit count **both ways** in the same
`superRefine`, and the obvious move was to copy it. The asset half is a
`.transform` instead, for two reasons that agree:

1. **A refusal has to be shown.** The panel hides this control on exactly the
   types the converse rule is about, so the error would highlight something
   nobody can see — the failure the Select's own `invalid` comment was added to
   fix.
2. **A refusal could not be obeyed.** Clearing the value on the way out and
   restoring it on the way back was implemented first and traced on
   2026-09-02: the effect's write lands and reads back, and then the freshly
   mounted Radix `Select` reports its own empty value through `field.onChange`
   and takes it away again. Writing to that control in the commit that mounts
   it loses.

Blanking in the schema needs no timing to be right, and holds whatever the
hidden picker contains — including the `'new'` sentinel.

### What moved

- `core/types.ts` — `targetsAsset(type)`, beside `movesPosition`. Its
  `PORTFOLIO_LEVEL` list is **module-private, unlike `POSITION_MOVING`**: the
  predicate is the whole API, and a second exported name for one fact is only a
  way to ask the question wrongly. Membership is pinned by an exhaustive
  `Record<TxType, boolean>` in `derive.test.ts`, which will not COMPILE if a
  tenth type appears — the predicate is a negation, so a new type would
  otherwise join the majority in silence.
- `core/schemas.ts` — `assetId` loses `.min(1)`; the refinement requires an id
  where the type wants one, the transform blanks it where it does not.
- `TransactionPanel.tsx` — **the ledger row asks `targetsAsset(tx.type)`, not
  the id.** Three doors stopped WRITING a borrowed asset; none of them touches a
  row already stored, and nothing migrates one — so every deposit recorded
  before today still read «Внесок · Inzhur REIT» on screen, which is the symptom
  the report was about. This is the only change here that fixes existing data,
  and it was missed until the fourth review round.
- `TransactionPanel.tsx` — the «Актив» block goes inside `Reveal`; a
  `useLayoutEffect` clears the field's ERROR and never its value, before the
  frame the leaving control is painted in; the reset restores the picker from
  the SUBMITTING RENDER's watched value, since the parsed one has been blanked
  and `handleSubmit` awaits the resolver before `record` runs.
- **`pickedNew` and `isNewAsset` are two questions, and conflating them destroys
  typed input.** The first draft gated `isNewAsset` on the type, which is right
  for the quick-create panel and its validation — a deposit cannot bring an
  asset into existence — but the sub-form's RESET keyed off the same flag, so a
  glance at «Внесок» discarded a half-typed asset. Reproduced in the browser,
  twice. The reset now keys off the picker alone, and `onSuccess` resets the
  sub-form's ERRORS rather than resetting it: recording a deposit no longer wipes
  an asset the user was part-way through describing, and a failed quick-create
  press no longer leaves red borders standing over a later success. The VALUES
  need no reset there — the quick-create path moves the picker off the sentinel,
  which is the effect's trigger.
- `core/backup/json.ts` — the importer's referential check asked `assetId !== ''`
  and skipped itself entirely for an empty id, so `{ type: 'buy', assetId: '' }`
  imported cleanly. New issue code `asset-missing-on-position-row` with its uk/en
  copy and its `renderIssue` sentence, keyed to **`movesPosition`, not
  `targetsAsset`** — see the section below. The converse is a `.transform` on
  the row array, blanking an asset a portfolio-level row names, which is what
  every pre-D129 export contains.
- **`BACKUP_FORMAT_VERSION` 4 → 5.** [`D122`](D122.md)'s rule read straight: a
  v4 build accepts a `buy` with no `assetId` and this one does not. Not bumping
  was tried, on the ground that no build ever WROTE that shape — but the version
  tracks the READER, [`D128`](D128.md) proved the same of 4 without unmaking it,
  and D122's own words are that two live builds calling themselves one version
  and disagreeing about what they accept is the thing the number exists to
  prevent. A v4 build IS live: dev deploys on every push. The normalized converse
  does not enter into it — every v4 file stays readable through it.
- `infra/schema/user.ts` — a stale clause in `transaction_asset_absent_ck`'s
  comment, which asserted that the app fills `assetId` on all nine types.
- `docs/reference/w7-migration-translations.md` — item 3 marked DORMANT (the
  class item 4 already belonged to), item 2 restated as still owed.

### W7's schema already forbade it

`infra/schema/user.ts` carries `transaction_asset_absent_ck` —
`type NOT IN ('deposit','withdrawal') OR asset_id IS NULL` — and its own comment
named this bug without recognising it as one:

> …would reject every deposit the app records today (`schemas.ts` fills
> `assetId` for all nine transaction types)…

That was read as a reason to keep the constraint one-way. It was in fact a
migration that would have rejected every deposit the owner had recorded, and the
app was the side that was wrong: the seed, the backup importer and the ledger row
were already on the DDL's side. The comment is corrected; the two one-way rules
stand, because `tax` still needs the freedom to name no asset.

**This does NOT discharge the migration.** `asset_id` is a `uuid` and the
column's own comment reads *NULL for portfolio-level rows, never `''`* — and
`''` is not a uuid. What D129 does to item 3 of
[`w7-migration-translations.md`](../reference/w7-migration-translations.md) is
make it DORMANT, on the same footing as item 4 and for the same reason: only a
store written before 2026-09-02 holds a borrowed id, and D128 says no such store
migrates. Dormant is not retired — a first draft here struck it through, which
reads as «this can never be needed», and that file exists partly to be right on
the day a real user's data does move. Item 2 — translate `''` to NULL, do not
copy — is untouched and owed.

### The form's rule and the store's are not the same rule

**`targetsAsset` is the FORM's question, not a mirror of the CHECK.**
`transaction_asset_present_ck` requires an asset only on the four
position-moving types and deliberately permits a `tax`, a `dividend_accrual` or
an `interest_payout` with none. This form has always asked for one on those
three — the field carried a bare `.min(1)` for all nine types before D129 — and
D129 did not loosen it. That is a narrower rule than the store's, which the form
is allowed to choose and the store will still accept. The two agree exactly
where it matters: `transaction_asset_absent_ck` forbids an asset on the same two
types `PORTFOLIO_LEVEL` names.

**Which is why the importer does not use it for the required half.** The first
attempt wired `targetsAsset` into `integrityIssues`, making the backup stricter
than the store it mirrors — so the day anything put `{ type: 'tax', assetId: '' }`
into Dexie, that database could not export (the guard re-reads its own output),
could not be imported into (the pre-import safety backup IS that export) and
could not be backed up before a wipe. That is [`D126`](D126.md)'s deadlock,
re-created for the sake of making two doors look symmetrical. The importer now
requires an asset with `movesPosition`, which is `transaction_asset_present_ck`
exactly, and uses `targetsAsset` only for the converse — the half where the form
and the store agree.

### `Reveal` was tried on the quick-create panel and reverted

D129 gave `isNewAsset` a second trigger — the TYPE — so choosing «Внесок» now
plays the picker's 300ms slide-out directly above a dashed panel that vanishes
in the same frame. A review round called that a violation of the working
agreements' *nothing pops or snaps*, and it is one. Wrapping the panel in
`Reveal` was the obvious answer and it is the wrong one; measured in Chrome, it
made four things worse:

| | |
| --- | --- |
| the snap | `Reveal` animates opacity and translate, **never height** — the wrapper held its 593px for the whole exit, so the collapse moved from t=0 to one frame at t=300. Bigger, later. |
| the fields | the `!pickedNew` effect fires at t=0 and now lands on live DOM, so «Назва» visibly blanks itself 230ms before the node is removed |
| form state | RHF repaints «Назва» but not «Код»; re-entering inside the window reuses the same nodes, so the visible «Код» disagrees with state and submitting reds a field showing a valid value |
| focus | ten controls stay hit-testable and in the tab order while leaving — `Reveal` marks nothing `inert` — and focus lands on `<body>` when the node goes |

A pop is worse than nothing; those four are worse than a pop. **The exit this
panel wants is a height animation plus an `inert` subtree, and both belong in
`Reveal` itself** — a change to a component nine other places use, which is not
D129's to make. The panel keeps its bare `&&`, the reason is pinned by a test,
and the motion gap is recorded here rather than closed badly.

### What did not move

No stored row. `Transaction.assetId` keeps its type and its documented meaning,
and the seed is untouched — this change makes the form agree with what the seed,
the ledger row and the DDL already said. `derive.ts` moved only in its comments.
Measured after: the demo records a deposit with `assetId: ''` and a key set
byte-identical to the seed's — `id,date,type,assetId,amount,source`.

**Two things DID move that an earlier draft of this section denied.** A pinned
figure: the version literal, in six places. And what a valid file may contain —
after 4 → 5 no existing backup passes the version gate at all, the demo's own
export included. That is the bump's cost, not a side effect of it, and it is
accepted on D113's standing grounds: one user, no real data, and a dataset that
can be re-seeded. Both sentences were written while the bump was still declined
and survived the reversal; they are corrected here rather than quietly dropped,
because the reversal is the interesting part of this entry.

### Not closed by this

GitHub issue [#19](https://github.com/RomanKushyk/investment-tracker/issues/19)
asks for strict validation, dependent inputs and auto-selection across the whole
transaction form. This is one dependent input, reported separately as a defect;
the guides, the option narrowing and the `type → source` auto-selection it also
asks for are not done, so #19 stays open.
