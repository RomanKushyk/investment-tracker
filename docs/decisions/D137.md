## D137 — deletion: batched application cascade, plus non-cascading keys (2026-09-03)

`PLAN-OPEN.md` **O33** has been open since 2026-08-27, surfaced while relocating
A51's schema-draft header. It asked whether W7 keeps the hand-written cascade or
adds tombstones, and [D101](D101.md) widened it on 2026-08-28 to include a third
option — real foreign keys — while ruling that W7 itself would ship none.

## The ruling

**Deletion is an application cascade, in batches, children first and the parent
last — and the schema declares NON-CASCADING foreign keys.**

```
LOOP  DELETE FROM user_price  WHERE asset_id = $1   (batched under the ceiling)
LOOP  DELETE FROM transaction WHERE asset_id = $1   (batched too — see below)
LAST  DELETE FROM asset       WHERE id = $1
```

**The action is `NO ACTION`, not `RESTRICT`, and the correction is recorded
rather than quietly applied.** The owner ruled the SHAPE — a batched application
cascade with real, non-cascading keys — and named `RESTRICT`; a code review
found that `RESTRICT` breaks this ruling's own second step, so the action inside
the ruled shape changes. **`RESTRICT` is checked immediately, per row;
`NO ACTION` defers to the end of the statement.** The self-referential key
`settles_payout_id → transaction(user_id, id)` makes that decisive: a `tax` row
settling a payout **carries the same `asset_id` as the payout** — the schema
comment on `transaction_asset_absent_ck` says the spec requires an asset on a
tax row *"only when the tax relates to a payout"* — so both rows are removed by
the **one** `DELETE FROM transaction WHERE asset_id = $1`. Under `RESTRICT` the
payout is refused `23503` the moment it is processed before its tax row, and
the asset becomes undeletable. Under `NO ACTION` both are gone by end of
statement and the check passes. AWS's guidance names both actions; only one of
them works here.

**Both child deletes are batched, and the first draft batched only one.** D101's
own ground — quoted approvingly below — is that transactions per user are
*"unbounded or unpredictable"*. That is the same argument that forces batching on
`user_price`, so a single `DELETE FROM transaction` meets the identical 3 000-row
ceiling. Looping only the price table would have left the failure in place on the
table D101 actually named.

**Tombstones are rejected.** Nothing in this project has asked for undo or for
retention, and a `deleted_at` is not a free option: it puts a filter in every
read, and the first forgotten one renders deleted data as live. Its usual
justifications — regulatory retention, an undo affordance, referential history —
are all absent here.

## The measurement that decides it

**DSQL's transaction ceiling is 3 000 mutated rows**
(`2026-08-04-cloud-stack-and-cost.md`). `user_price`'s primary key is
`(user_id, asset_id, as_of)` (`infra/schema/user.ts`), i.e. **one row per asset
per date**. So a single asset carrying a decade of saved prices is on the order
of **3 650 rows**, and deleting it in one statement fails.

Batching is therefore not a refinement — it is the only shape that works at all
once history accumulates. **Parent last is what makes it resumable**: a failure
midway leaves the asset present with some prices gone, which a re-run finishes.
Parent first would leave rows with nothing above them.

## The code is identical either way — which is why the key does not cascade

The non-obvious part, and it inverts the usual argument for cascades.
[D101](D101.md) records AWS's `CREATE TABLE` guidance:

> cascading actions **count towards the transaction modification limit** … prefer
> `NO ACTION` or `RESTRICT` for foreign key relationships where child-row
> cardinality is unbounded or unpredictable

So **`ON DELETE CASCADE` would not have removed the batching** — the cascaded
rows count against the same 3 000. A cascading key buys nothing here and
introduces a failure the application cannot work around, because the database
decides the cascade's extent. A non-cascading key has neither problem: it cascades
nothing, so it never interacts with the ceiling, and AWS names both
`NO ACTION` and `RESTRICT` as preferred for exactly this shape. **Which of the
two is settled above, on a reason that has nothing to do with the ceiling.**

**What the key is FOR, then, is the second writer.** With the application
cascade alone, a future writer that forgets a step leaves orphaned `user_price`
rows — and reads go `asset → user_price`, so those orphans are **invisible to
the application** and simply accumulate. Under the key the same mistake is
refused `23503`. The second writers are not
hypothetical: **W8's super-admin surface and Phase 7's DB browser are both
planned**.

**The nightly integrity audit is not a substitute, and its own log says why.**
`../superpowers/specs/data-model/ledger.md` specifies one, and it would find
orphans — after the fact. `RULES.md` records eight independent instances of the
same defect in this project: *a green indicator that was green because nothing
had been attempted*. An orphan audit is green from day one and stays green until
the day it matters, which is the day it must be trusted.

## Two of D101's three grounds had evaporated

Recorded because a ruling that reverses another should say what moved, not
merely that it disagrees.

| D101's ground | Status on 2026-09-03 |
|---|---|
| *"`RESTRICT` is not free in the client. `deleteAsset` deletes the asset and **then** its transactions — an order a real key would refuse. Adopting keys means reversing it."* | **Gone.** The reversal is required by **batching**, for resumability, whether or not a key exists. The cost is paid by the application cascade alone, so it is no longer a cost *of keys* |
| *"A key added after the fact is permanently `NOT VALID` … the rows W7 migrates would never be verified. So adopt only behind a clean integrity audit."* | **Vacuous at W7.** Drizzle emits keys as post-hoc `ALTER TABLE` (`infra/docs/dsql-alter-limits.md`), and at W7 that `ALTER` runs against **newly created, empty** tables — and [D128](D128.md) has W7 seeding fresh data rather than migrating any. There are no pre-existing rows for the key to skip, so every row it will ever see is checked. The precondition is met by there being nothing to audit |
| *"AWS's guidance points away from the interesting half … prefer `NO ACTION`/`RESTRICT` where child-row cardinality is unbounded."* | **Stands — and now argues FOR this shape.** D101 read it as a reason to skip keys; it is a reason to skip **`CASCADE`**. Both of the actions it names are non-cascading, and this entry picks `NO ACTION` |

D101's ruling is amended, not erased: **it was right that `CASCADE` is the wrong
half**, and right that nothing forced a decision in 2026-08. What it could not
know is that batching would be mandatory for an unrelated reason, which is what
retired its first ground.

## What this costs

**A third promotion rewrite rule.** `infra/migrations/drafts/README.md` records
two — insert `ASYNC`, strip `USING btree` — and a key needs a third: **append
`NOT VALID` to every generated `ALTER TABLE … ADD CONSTRAINT`**, or DSQL refuses
it (`infra/docs/dsql-alter-limits.md`). That rule is a property of the generated
file, applied uniformly, exactly as the other two are.

**One shape the schema permits and the application never writes** — named so it
is not discovered at implementation. `transaction_settles_ck` requires only that
a settling row be a `tax`; nothing requires that tax row to carry an asset. A
`tax` with `asset_id IS NULL` settling a payout with `asset_id = X` is therefore
legal, and it is **not in the delete set at all**, so the payout's deletion is
refused permanently rather than resumably. Two remedies, neither picked here: a
CHECK mirroring the domain's `targetsAsset` (a `tax` that settles carries the
asset), or an explicit prior step deleting rows that settle rows about to go.
**W7's schema task owes one of them**, and until then the app's own invariant is
what keeps the shape from arising.

Otherwise nothing. Measured for this schema's shape and already written down:
**a composite key on a NULLABLE column behaves correctly** under `MATCH SIMPLE`
(a `deposit` with `asset_id IS NULL` is not checked; a `buy` pointing at nothing
is refused `23503`), **self-referential keys work** for `settles_payout_id`,
**`ON DELETE RESTRICT` refuses** as measured in D99 round 3 — which is what recommended it before the self-referential key was thought through, and **no index is
created per key**.

## Issue #34 was never reachable here

[#34](https://github.com/RomanKushyk/investment-tracker/issues/34) — deleting an
asset destroying old deposits that borrowed its id — is a property of **today's
Dexie store**, where `deleteAsset` cascades on the `assetId` field rather than
on the row's type. **On the target schema it cannot happen**, with or without
keys: `transaction.asset_id` is nullable and two CHECKs force
`deposit`/`withdrawal` to carry `NULL`, so no cascade can reach a
portfolio-level row. This ruling neither fixes #34 nor is blocked by it — the
issue is about the code that runs until W7, and `W7-API-CONTRACT.md`'s
instruction not to port the field-based semantics stands.

## What this does not decide

- **Whether the ledger is append-only in practice.** `ledger.md` says *nothing
  is ever deleted, so there are no cascades*, while `repository.ts` ships
  `deleteTransaction`. That tension predates this ruling and is not resolved by
  it.
- **`clearAll` and `dataset.replace`.** Both mutate far more than one asset's
  worth of rows and meet the same ceiling; batching them is W7's problem and the
  cost estimate in the cloud-stack spec (*"`clearAll()` crosses it ~year 11"*)
  **was computed against the old one-row-per-snapshot model and is not reliable
  under the `user_price` grain** — flagged here, not corrected.
- **Which other tables take keys.** This entry rules the shape and the action;
  the full reference list belongs to the schema task.
- **Deleting a USER.** `W7-API-CONTRACT.md` §3 notes that an `active` user
  owns a ledger and called that cascade O33's. It is not this entry's: O33
  asked about `deleteAsset`, and a user delete crosses every table at once,
  including `app_user` itself. **Closing O33 would have orphaned that
  question**, so it is named here and left with W8, where the super-admin
  surface that could perform one lands.
