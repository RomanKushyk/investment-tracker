## D60 — The repository is public, writable by one account, and rewritable by none (2026-08-14)

Public read, single writer, and a history that cannot be rewritten by anyone —
including the owner. Set 2026-08-14, after the prod/dev split (D59) gave the
repository a branch whose contents are a live site.

**Nothing had to be taken away to get read-only for others.** The repo has exactly
one collaborator — the owner — no deploy keys, and no pending invitations. The work
account that shares the machine's `gh` keyring already resolves to `push=false`
here. Public visibility grants read, never write; the fear it does is the reason
this entry states it.

**The ruleset binds the owner too.** `protect-long-lived-branches` covers
`refs/heads/main` and `refs/heads/dev` with `deletion`, `non_fast_forward` and
`required_linear_history`, and **`bypass_actors` is empty on purpose**. A rewrite is
still possible — by editing the ruleset first, which is a deliberate act rather than
a `--force` typed at the wrong moment. Verified by reading back what GitHub says
applies to each branch, not by trusting the create call.

**No merge commits, enforced in two places.** `allow_merge_commit` is off at the
repo level, and `required_linear_history` rejects one that arrives by push. Rebase
and squash remain; promoting `dev` into `main` is a fast-forward, which creates no
merge commit and stays legal.

**The dev branch is behind basic auth, production is not.** Amplify's branch-level
access control answers 401 on both `dev.quirenote.com` and the Amplify dev URL —
branch scope, not host scope, so there is no second door. Production carries none:
it is the published app, and an auth wall there would be a different product.

> **Asked the same day: is hiding dev worth anything when the repo is public?**
> The honest answer is that it buys **audience, not secrecy**, and it was never
> capable of buying secrecy. Everything on that host is public already — the
> source, the design references, the plans, and the demo seed it serves, which is
> the same seed anyone gets by cloning and building. Someone who runs
> `pnpm build` reproduces dev exactly, and no password on a URL changes that.
>
> What it does close is the gap between *reproducible by anyone who compiles it*
> and *one click away*: no search indexing, no link that can be pasted into a
> chat, no screenshot of a half-finished feature circulating as though it were
> the product. That gap is real even when the code is open, because a running
> instance is a different artifact from source.
>
> It is worth naming what it costs, since the cost is not zero: a shared
> credential to store and rotate, and friction for anything that checks dev —
> `navigation-map.md` now has to say so, and a future smoke test would need it.
> If that friction ever outweighs the benefit, the cheaper half-measure is
> `X-Robots-Tag: noindex` on the dev branch, which stops indexing but not link
> sharing.
>
> And the asymmetry is worth seeing clearly: the public repository reveals
> unfinished work — commits, briefs, plans — far more thoroughly than a deployed
> build does. This closes the smaller of the two holes. It is still worth
> closing; it is not worth mistaking for protection.

**What actually protects production is the shape of the pipeline.** Quality gates run
before the job assumes any AWS credential; the `prod` environment accepts only
`main`; the deploy role can call four Amplify actions on two named branches and
nothing else. The one exposure left is egress cost — and the existing $5 budget was
checked for SUBSCRIBERS rather than existence, because this project has found six
separate green-because-nothing-was-attempted indicators (see the note under D53).
It has three thresholds and a live email on each, plus a daily anomaly subscription.
