## D99 — DSQL refuses `USING btree`, so promotion rewrites an index line twice (2026-08-27)

Working: [`../../infra/docs/dsql-ddl-first-contact.md`](../../infra/docs/dsql-ddl-first-contact.md).
Closes the pre-condition on W7's row in
[`../plans/phase-w-i-ii-iii.md`](../plans/phase-w-i-ii-iii.md), six days before
its 2026-09-02 gate.

**The answer is no.** `USING btree` is rejected with and without `ASYNC`, and
a plain `CREATE INDEX` carrying no `USING` at all is rejected too:

```
CREATE INDEX       … USING btree (…)  -> 0A000  USING not supported for CREATE INDEX
CREATE INDEX ASYNC … USING btree (…)  -> 0A000  USING not supported for CREATE INDEX
CREATE INDEX       … (…)              -> 0A000  unsupported mode. please use CREATE INDEX ASYNC.
CREATE INDEX ASYNC … (…)              -> job_id
```

**So `infra/migrations/drafts/README.md`'s promotion rule was half a rule.** It
said promotion converts every `CREATE INDEX` to `CREATE INDEX ASYNC`. Doing
only that produces a statement DSQL refuses. Promotion applies **two**
transformations to every index line, uniformly or not at all: insert `ASYNC`,
and strip `USING btree`. Both stay out of the generated file for the same
reason as before — `ASYNC` is a syntax error on stock Postgres, and `USING
btree` is what drizzle-kit emits and what
[`../../infra/src/user-schema.test.ts`](../../infra/src/user-schema.test.ts)
needs in order to apply the file to PGlite.

**The cause is not what the documentation implied.** DSQL's published
`CREATE INDEX` grammar omits the `USING` clause entirely, which reads as "there
is no `USING` here". There is: `USING btree_index` is accepted, and
`pg_get_indexdef` prints every index — primary keys included — in exactly that
form. `pg_am` holds `btree` alongside `btree_index`, so the refusal is a
whitelist of one access-method name, not an unknown identifier. Reasoning from
the grammar would have reached the right verdict through a wrong mechanism and
left `USING btree_index` looking impossible; it is possible, and still wrong to
use, because a DSQL-only spelling in the promoted file buys nothing over
omitting the clause and costs the PGlite test.

**Accepted is not built.** `sys.wait_for_job` is a procedure — `SELECT`ing it
gives `42809 … is a procedure` — so the first round's two index jobs sat at
`submitted`/`indisvalid = false` and it could claim only that the DDL parsed.
`CALL sys.wait_for_job(job_id)` returns `succeeded`, `sys.jobs.status` reaches
`completed`, and only then does `indisvalid` turn true. **D48** already found
the timing half of this from the outside — an index that measured as absent 25
seconds before it measured as present. The W7 migration runner must `CALL` and
check, because the documented failure mode is a job ending `failed` and leaving
an `INVALID` index definition behind. That last part is DOCUMENTED, not
measured: AWS says the definition is not auto-removed and must be dropped by
hand, and no job was made to fail in any of the three rounds — both real jobs
reached `completed`. Whether `DROP INDEX` clears an INVALID async index on this
cluster is untested, and the W7 runner should not assume it.

**Everything else in the file applies, and its constraints bite.** All seven
statements ran against the live cluster: five tables, five primary keys — four
of them composite, `app_user` keying on `user_id` alone — 20 `CHECK`s, three
`UNIQUE`s, one `DEFAULT`, and `numeric` with no precision.
`app_user_status_ck`, `app_user_role_ck`, `app_user_decided_ck` and
`app_user_email_uq` each rejected a row aimed at it, and `DEFAULT 0` landed.
That retires the drafts README's second open risk — "no precedent against the
real cluster" — for these three constraint kinds. It also shows DSQL's
index-organized primary key directly: `account_user_id_id_pk` comes back as
`USING btree_index (user_id, id) INCLUDE (provider, name, created_at)` — its
three non-key columns carried in the primary key's own index, which nothing in
[`../../infra/schema/user.ts`](../../infra/schema/user.ts) asked for. Two
tables were read back this way, not five, so the general form stays
documentation.

**And DSQL has foreign keys.** The drafts README stated as fact that
`REFERENCES` is absent from the grammar — corrected in this branch. It is
not, and this was measured composite — the shape this schema would need — and
enforced in both directions, `ON DELETE RESTRICT` included. **Nothing is decided about using them**: they
would displace the application-enforced integrity plus nightly audit that
[`../superpowers/specs/data-model/ledger.md`](../superpowers/specs/data-model/ledger.md)
specifies, and their cascade actions interact with DSQL's 3,000-row
transaction limit. Filed as
[`../plans/PLAN-OPEN.md`](../plans/PLAN-OPEN.md) O34 — a bodiless row, because
the row is the whole question — and it is answered together with O33, whose two
candidate answers one of them now is. O34 is a question, not a plan.

**One thing this entry could not be written without changing.** `pnpm decisions`
refused to add it: `src/decisions/render.ts` threw at 201 lines, enforcing a
hard 200-line wall on `README.md` while its own comment claimed to mirror "the
same cap `src/docs-line-cap.test.ts` enforces for every Markdown file" — which
**D98** had made false earlier the same day, by turning that cap into a
per-file ratchet. A guard left behind by a decision it was supposed to follow
is a guard that blocks the next author for a reason nobody meant. The wall is
removed; the generator now prints the diagnostic question and writes, and the
file's length
is pinned at 201 in `distillation-baseline.json` like any other over-200 file.
**Where that index's growth should actually go is not settled here** — every
shape breaks a rule pinned in `CLAUDE.md`, and a session adding a decision is
the wrong session to redesign the log. Filed as
[`../plans/PLAN-OPEN.md`](../plans/PLAN-OPEN.md) O35, with the cost of leaving
it: from now until it is answered, each new decision needs a reviewed
`pnpm distillation-baseline` alongside `pnpm decisions`.

**What this does not settle.** Only the DDL was exercised. Nothing here says
anything about the migration runner's replay problem — the drafts README's
"the generated DDL is NOT replayable" stands untouched, and first contact
confirmed why: every statement is a bare `CREATE`, and a second run of the
whole file would die on statement one.
