## D110 — A Dependabot PR merges by hand, and three things the runbook had wrong (2026-08-29)

The first dependency bump this repository ever merged: PR #28, react-router
7.18.1 → 7.18.2, GHSA-qwww-vcr4-c8h2. Everything below was measured on it.

### The ruling: merge locally

`gh pr merge --squash` preserves the PR author, so it would have put a commit
authored by `dependabot[bot]` on `dev`. [`D104`](D104.md) exempts the branch NAME
from `D73`'s convention and nothing else; `CLAUDE.md` pins authorship to the
owner's personal identity. Owner's call, asked before the merge rather than
discovered after — `dev` forbids force-push, so the commit would have been
permanent and the precedent set by accident.

The mechanism changes; the link does not. `Closes #28` in the commit body closed
the PR at push, because `dev` is the repository's default branch, and Dependabot
flipped alert #6 to `fixed` — both confirmed on the first poll afterwards.

### `pnpm.overrides` in `package.json` is dead, and fails as a WARNING

```
[WARN] The "pnpm" field in package.json is no longer read by pnpm.
       The following keys were ignored: "pnpm.overrides".
```

`pnpm install` then succeeds, the lockfile is untouched, and all four gates pass
green on a change that did nothing — `grep -c 'esbuild@0.18.20' pnpm-lock.yaml`
still returned 2. The runbook prescribed exactly this form. **Its own thesis is
that these paths fail silently, and it failed silently on its own worked example.**

Overrides live in `pnpm-workspace.yaml`, which this repository already has.
Scope them to the parent AND bound the range —
`'@esbuild-kit/core-utils>esbuild': '^0.28.1'` — not to the bare package and not
to an open `>=`: the surgical form let `core-utils` dedupe onto the `0.28.1`
that vite and tsx already pull, taking the tree from three esbuild copies to two,
while a blanket override would move vite, vitest and drizzle-kit off their tested
ranges for no extra coverage. The bound matters for the same reason the scope
does: `>=0.25.0` re-resolves to the newest match on every lockfile-regenerating
install — the install this path prescribes — so the first esbuild past the range
vite and tsx float in would hand core-utils a copy nobody else has, and the dedupe
would be gone. `^0.28.1` tracks that range instead of running ahead of it, and any
0.28.x satisfies the advisory.

### The discriminator is the parent's RANGE, not transitive-vs-direct

The runbook said a transitive advisory means `pnpm update <pkg>` "is a no-op on
the lockfile entry that carries the advisory". False on pnpm 11.10.0, whose
`--help` documents `--depth <number> … Infinity is default`. `@eslint/eslintrc`
declares `js-yaml: ^4.3.0`, which admits the fix, and `pnpm update js-yaml` moved
it to 4.3.2 in four lockfile lines with `package.json` untouched. Following the
old rule would have sent that to an override it did not need.

The rule is right about esbuild and right by accident: `@esbuild-kit/core-utils`
pins `~0.18.20`, so the fix is outside every parent's range — and that package is
deprecated, so no future release will carry it.

### `pnpm build`, and the absence of any check at all

`tsc --noEmit`, eslint and vitest resolve modules through Node and vitest. Only
`vite build` resolves through the production `exports` conditions, so a bump whose
`exports` map changed passes all four gates and breaks at build — after the merge,
on `dev`, taking the deploy with it.

That matters more than it looks, because **`gh pr checks 28` reports "no checks
reported on the … branch"**. Both workflows trigger on `push` to `dev` or `main`,
and this repository has no `pull_request` trigger anywhere. The runbook warned that
"a green Dependabot check is not this repository's gate"; the sharper fact is that
there is no check to be green. The local gates are the only ones that run before a
bump reaches the deploy branch.

### What this does not decide

Whether to add a `pull_request`-triggered gates job. It would make a
`dependabot/*` branch verifiable before the merge rather than after, and it is a
real change to this repository's CI shape — left open on purpose.
