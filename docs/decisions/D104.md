## D104 — What the repository uses GitHub for, and what it deliberately does not (2026-08-28)

Owner's rulings, 2026-08-28, the session after [`D103`](D103.md) moved the inbox
to GitHub Issues. **This entry covers the GitHub surfaces only.** Two rulings of
the same day were split out when a draft of this entry tripped the 200-line
diagnostic, whose question — does this file hold a second purpose? — answered
yes: the work order is
[`D105`](D105.md), and the dated gates — closing D103's "a reminder is the
candidate" — are [`D106`](D106.md). D103's other open candidate, that finished
work is invisible, is answered in part below.

### 1. The wiki is OFF

Never initialised, so nothing was lost turning it off. **Two mechanisms hold
this documentation honest and a wiki has neither.** `pnpm test` reads it — the
claim ratchet, the line cap, the decisions index and the fact fences all fail
the suite on a file in this tree, and none can see a wiki page. **Two drafts of
this line got CI wrong before it was measured, so the measurement is here, read
off the two files:** neither workflow has a `pull_request` trigger;
`deploy-frontend.yml` fires on `push: [dev, main]`, `deploy-backend.yml` on
`push: [dev]` only, and both carry `workflow_dispatch`. So the suite never runs
on the branch a change is reviewed on. It runs after the
squash-merge and gates the **deploy**, not the landing, and only when a changed
file escapes `deploy-frontend.yml`'s `paths-ignore` (`**/*.md`, `docs/**`,
`infra/**`, `.github/workflows/deploy-backend.yml`) — which a docs edit touching
root-level `claim-baseline.json` does. Before a change lands the suite is the
author's to run. And **D76
reviews documentation before it lands**, on evidence that came from this
repository's own Markdown; a wiki keeps per-page revision history, so *a* diff
exists, but nothing stands between an edit and publication.

**Two things this ruling deliberately does NOT claim, because both are false
here:** a wiki has no pull request, and neither does this repository (D73 — "no
PR is required"); and `format:check` never reads Markdown at all,
`.prettierignore` excluding `*.md` at every depth. The first draft of this entry
claimed both, and the D76 review caught them — the second time in one change
that a mechanism was asserted without being checked against this repository's
own configuration.

### 2. Dependabot is security-only

Alerts and automated security fixes are on, as repository settings. **There is
deliberately no `.github/dependabot.yml`, nor the `.yaml` GitHub equally honours** — that file is what enables routine
version-bump PRs, and this repository carries **three ecosystems**: 45 packages in the root pnpm
tree (20 + 25), 5 more in `infra/` under npm with its own `package-lock.json`,
and the pinned GitHub Actions, which have no manifest at all. They would arrive in a steady stream from two
directions, and every merge here costs a `/code-review` (D76), so version churn
taxes the gate that protects the app while buying no security.

**The alert is the unit, not the PR** — measured the same hour: 7 alerts, 3
open, 1 PR. Two open advisories had no PR at all, so draining the PR list would
have left them.

**This narrows two standing rules, which is why they are in `amends`:** D73's
branch naming, since a Dependabot branch is `dependabot/…` and not
`<type>/<kebab-title>` — the exception is the name, never the gate; and D76's
premise that there is "no PR to hold" declined findings, since here there is
one.

**The runbook is [`../reference/DEPENDABOT.md`](../reference/DEPENDABOT.md)** —
which commands apply to which manifest, and which steps fail silently if
skipped. It is there and not here because it carries figures and commands that
change; this entry carries only the ruling.

### What was built rather than ruled

**Fourteen GitHub Releases**, created from the existing annotated tags
`v1.0.0`…`v1.8.0`. The prose was already written and reachable only by
`git for-each-ref`; each release takes its title from `%(contents:subject)` and
its notes from `%(contents:body)`, so the annotation stays the single copy.
**Not `--notes-from-tag`**, which sounds right and is wrong: measured against
gh 2.95.0 it takes `%(contents)` — subject, blank line, body — and would repeat
the title inside the notes. `VERSIONING.md` step 6 carries the command and the
measurement. Four tags carried a subject and no body, and their releases say so.

This **partly** answers the other candidate D103 left open — that finished work
is invisible. Measured for this entry rather than inherited, and the two halves
must not be added together: **`plan.closedTasks` is 53 and counts PLAN A ONLY**
(`src/facts/facts.ts` counts rows in `docs/archive/plan-a/README.md`), whose
bodies are exactly the **16** files beside it. `plan-b/` and `plan-c/` hold **5
further closed items** — W1, O20, O23, O24, O25 — across 3 more files and their
own ledgers. So it is 53 over 16, or 58 over 19; never 53 over 19. The live
state needs the 12 files now in `docs/plans/`.

D103 said "14 files plus the ledger" for `docs/archive/`. The ledger is real —
`plan-a/README.md` — so only the count is wrong: **16 bodies, not 14.**
Superseded by the figures above; no explanation for the 14 is offered here,
because none was verified.

**Releases answer the version half and only that.** They make shipped work
visible per version; they do not make the current plan state visible, so a
generated board over `docs/plans/` remains unfiled, and unruled.
