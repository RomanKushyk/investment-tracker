## D57 — The theme is one list of values, stamped as an answer (2026-08-13)

**Phase 5, A9.** The app has light and dark. Three choices are load-bearing and
none of them are the obvious one.

### `system` is a preference, never a value

The store holds `light | dark | system`. What the page WEARS is
`resolveTheme()`'s answer, stamped on the root as `data-theme="light"|"dark"`.
Keeping the two apart is what lets an OS flip reach a user sitting on `system`
without rewriting their stored choice — if `system` resolved at write time,
"follow the system" would decay into "whatever the system was when I last
looked". It also means CSS never has to express `system`: the media query lives
in the one place that reads it, beside the `matchMedia` listener that keeps it
live.

### One palette, redefined — not two palettes

`[data-theme='dark']` redefines the 38 palette tokens and nothing else. The 19
`--color-chart-*` aliases are declared as `var(--color-reit)` and resolve against
whatever wins on the same element, so they follow automatically — verified at
runtime by overriding a base token and watching the alias move. Redeclaring them
would be 19 more values able to disagree with the ones above.

The block is unlayered on purpose: Tailwind puts `@theme` in `@layer theme`, and
an unlayered rule beats a layered one regardless of source order.

A related asymmetry, and the one that costs an afternoon if unknown: `.bg-page`
emits `background-color: var(--color-page)` — a runtime seam, so redefining the
token moves it — but `.shadow-card` INLINES its value at build time. Shadow
tokens must be called as `shadow-(--shadow-card)`, never `shadow-card`, or the
dark theme cannot reach them.

### The first paint belongs to a head script, and to nothing else

`index.html` reads `state.theme` out of localStorage and stamps the attribute
before the module bundle exists; `useTheme()` owns every write after that. Two
writers would be one too many. The script cannot import the store's sanitizer, so
the duplication is real and `src/app/theme.test.ts` pins the two against each
other — an unknown stored value must resolve to `system` in both, and the
attribute must never be left unset.

### What breaks when the shadows go

Dark zeroes every shadow (`0 0 #0000`, not `none`: they compose into Tailwind's
five-part list and `none` is not legal as a list item, which would invalidate the
whole declaration). The catch is that the LIGHT theme was leaning on those
shadows to separate two surfaces, so removing them breaks the separation:

- the segmented control's thumb falls to 1.09:1 on its track (1.20:1 in light),
  and the Switch knob to 1.19:1 — barely worse than the 1.24:1 it has in LIGHT,
  which is the point. `--shadow-thumb` is a 1px ring in dark and the light
  drop-shadow otherwise: four call sites, one token.
- the sidebar goes DARKER than the page (#0f0f11 on #141416 — the two planes
  meet at 1.1:1) and the dialog floats over the scrim with no boundary at all.
  `--color-surface-edge` is the same trade for them (2026-08-14).
- the filled button hovered to `sidebar-hover`, a RAIL token. In light that read
  as "ink, a little lighter"; in dark the rail token is dark while `bg-ink` is
  near-white, so hovering flipped the fill to #26262b under #141416 text and the
  label vanished. A fill's hover must move WITH the fill — hence
  `--color-ink-hover` (2026-08-14).
- sonner painted the toast from its own default theme: a #ffffff card in the dark
  app, the one surface that never turned. It now paints from the palette
  (2026-08-14).

Every one of those is the same defect: a token borrowed from another plane, or an
effect standing in for a boundary. Neither survives an inverted theme.
