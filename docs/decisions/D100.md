## D100 — A DSQL constraint can be added later, as `NOT VALID` and never validated (2026-08-28)

Working: [`../../infra/docs/dsql-alter-limits.md`](../../infra/docs/dsql-alter-limits.md).
Measured because **O34** — should the user schema declare foreign keys — cannot
be weighed without knowing whether the answer can be revisited. **This entry
answers nothing in O34.** It removes the reason to answer it in a hurry.

**The rule.** `ALTER TABLE … ADD CONSTRAINT` is refused bare and accepted with
`NOT VALID`, for `FOREIGN KEY` and `CHECK` alike. Such a constraint **enforces
every subsequent write** — measured: a violating row inserted beforehand was
tolerated, a violating row inserted afterwards was refused `23503` — and
**can never be marked validated**, because `VALIDATE CONSTRAINT` is itself
refused. `pg_constraint.convalidated` is `false` for life. A late foreign key
still carries its referential action: one added `ON DELETE CASCADE … NOT VALID`
cascaded.

**What is genuinely create-time-only** is narrower than "constraints", and
narrower than this entry's own first draft said: `NOT NULL` (which can be
DROPPED but never added), a column's TYPE, `UNIQUE` *as a constraint object*,
`PRIMARY KEY` — refused plain and refused `NOT VALID`, so **D30's premise is
now measured rather than inherited from the cloud-stack spec** — and a
`GENERATED … STORED` column. **`DEFAULT` is not on the list**: see below.
Uniqueness as behaviour is not on it either — `CREATE UNIQUE INDEX ASYNC` on a
populated table builds (`completed`, `indisvalid = true`) and then refuses
duplicates `23505`; over data that already holds duplicates the job ends
`failed` and leaves an invalid definition — `indisvalid = false`, really
present in `pg_class` — which a hand `DROP INDEX` then clears, executed rather
than taken from AWS's documentation as D99 had to. That settles the oldest
unmeasured caution in `infra/migrations/drafts/README.md`.

**O34 is therefore NOT dated**, and the point is sharper than that. Drizzle does
not put a foreign key inside `CREATE TABLE`; generated from a scratch copy of
[`../../infra/schema/user.ts`](../../infra/schema/user.ts) carrying two
references, it emits five `CREATE TABLE`s and then
`ALTER TABLE "account" ADD CONSTRAINT … FOREIGN KEY …`. So through this
toolchain **a foreign key arrives `NOT VALID` whether it is declared at W7 or
years afterwards** — declaring it now buys no stronger guarantee, only an
earlier one. If it is ever declared, promotion gains a **third** rewrite rule
beside D99's two: append `NOT VALID`, or the cluster refuses the statement.

The same generation retracts a claim made in passing: drizzle-kit's alphabetical
`CREATE TABLE` order does **not** break `account → app_user`, because the keys
are separate statements issued after every table exists.

**One live plan sentence stays narrowed, and by less than the first draft
said.** [`../plans/phase-w-i-ii-iii.md`](../plans/phase-w-i-ii-iii.md) says the
observation row's non-key columns "are an `ALTER TABLE` away and therefore not a
blocker" — the sentence that lets W3 and **O5** stay open. It holds for a plain
nullable column, for a `CHECK` added `NOT VALID`, and for a `DEFAULT` set later
(new rows only). It does **not** hold for `NOT NULL`, for a type change, or for
anything touching the primary key.

## How this entry was wrong before it was committed

Its first draft concluded, in bold, that **"a DSQL table can be subtracted from,
never added to"**, and dated O34 to W7's promotion on that basis. The probe
behind it sent one spelling — bare `ADD CONSTRAINT` — got `0A000`, tried the
same bare spelling for `CHECK` and `UNIQUE`, got the same error three times, and
generalised. The DSQL **release notes** had said otherwise for two days:
foreign key constraints shipped **2026-08-26**, with the `NOT VALID` route named
in the same sentence. That is also the precise date on which this repository's
"DSQL has no foreign keys" stopped being true, which **D99** could only place
as "some point nobody can now date".

**And it happened again inside the correction.** This entry's second draft
probed `DEFAULT` only as `ADD COLUMN … DEFAULT 0`, declared it create-time-only,
and propagated that into six files — while probing `NOT NULL` in two spellings
and column TYPE in its own. A code review caught it;
`ALTER COLUMN … SET DEFAULT` is supported and takes effect on rows inserted
afterwards. So W3 and O5 had been told a column default was undeferrable when it
never was. The same review's other prompt — that "everything else can arrive
later" asserted a closed set from about a dozen statements — produced the
`PRIMARY KEY`, `DROP NOT NULL`, `RENAME TO` and `GENERATED` rows above, one of
which turned out to be the fact **D30** has always rested on.

Recorded here rather than quietly fixed, because the failure is the exact one
the verifiable-documentation work exists to catch, committed twice by the entry
announcing a measurement: **one spelling measured, the general case asserted.**
It was caught by reading the vendor's release notes, which is where anything
about DSQL should be checked first — twice now that page has been ahead of the
migration guide, ahead of two AWS blog posts that still show application-level
foreign-key workarounds, and ahead of this repository.
