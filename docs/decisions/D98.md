## D98 — The cap becomes a diagnostic, and live plans split by section, not ID range (2026-08-27)

Two corrections to D95, both from the verifiable-documentation design's step 6
(`docs/superpowers/specs/2026-08-26-verifiable-documentation-design.md` §6),
landed on one branch — splitting the plans under the old hard cap would have
tripped it mid-move, so the ratchet had to land first.

**The cap is a diagnostic, not a wall.** D95's `src/docs-line-cap.test.ts`
failed the suite outright on any Markdown file over 200 lines. The design spec
called that the wrong shape: "a file over it holds more than one purpose, and
the fix is to find the second purpose" — a question a hard fail cannot ask,
only enforce.

**A file at or under 200 lines is unconstrained; a file already over it is
pinned and may not grow further.** `distillation-baseline.json` gains a fourth
section, `docLineCounts` (`src/distillation/doc-line-counts.ts`) — ONLY a file
already over the limit gets an entry, the same "zero counted, no row"
convention `commentChars` already uses — and `pnpm distillation-baseline`
regenerates it. Pinning every tracked file's exact length, not only the ones
over the limit, was tried first and reverted in review: it baselined the
length of `USER-FEATURES-DRAFT.md` and `USER-BUGS-DRAFT.md` — the owner's own
hand-edited draft files, never staged by an agent — as two integers in a
committed file, which is private uncommitted state leaking into the repository
by another name. Limiting the section to files already over 200 lines removes
that structurally: those two files sit at a few dozen lines by their own
"plain, bare bullets" rule and are nowhere near a candidate. `src/docs-line-cap.test.ts`
diffs `docLineCounts` directly with `src/claims/baseline.ts`'s own
`diffBaseline` — the identical over/stale primitive `distillation-lint.test.ts`
uses for its own three checks, one level down, rather than folding a fourth,
unrelated section into that module's own diff. D95's original worry — a file
reaching 2,211 lines unnoticed — is still caught: the moment any file crosses
200 lines it is pinned at that length, and it cannot grow further without the
regenerator being run and reviewed.

**Live plans split by section, the argument D96 already made for decisions.**
D95 named the plans' bodies for the IDs they held — `A01-A20.md`,
`A41-A50.md`, `A51-A60.md`, `W02-W08.md`, `W09-W17.md`, `O05-O29.md` — and D96
later removed exactly this shape from `docs/decisions/` because an append rule
and a line cap "could not compose." The plans never had an append rule, but
they inherited the other half of the same defect: a filename asserting an ID
range disagrees with the ordering principle the plan's own Status table uses
the moment a section is worked out of ID order, which had already happened.
`PLAN-NOW.md`'s own range table had to say so in words: "the range table runs
in ID order; section order is the Status table's, which puts Section P
(A52–A54) above Section M (A46)." A file-naming scheme whose own index has to
explain that it disagrees with the thing organising it is D96's argument,
restated for a second bucket.

**The rename, mirroring `docs/archive/plan-a/`'s own `section-<letter>.md`
convention:**

| Old | New | Holds |
|---|---|---|
| `A01-A20.md` | `section-c.md` | Section C |
| `A41-A50.md` | `section-m.md` | Section M |
| `A51-A60.md` | `section-p.md` | Section P |
| `W02-W08.md` | `phase-w-i-ii-iii.md` | Phases W-I, W-II, W-III |
| `W09-W17.md` | `phase-w-iv-v.md` | Phases W-IV, W-V |
| `O05-O29.md` | `still-open.md` | the still-open questions |

Plan A's Status table names its sections by letter, so those three names come
straight from it. Plan B and Plan C have no lettered column of their own:
Plan B's phases are the `#`-level headers each body file already carried
(`Phase W-I` … `Phase W-V`, joined when one file spans several); Plan C's one
file is named for the `# Still open` heading it already had. Neither name is
invented — both are text the document already carried.

**Moving is not rewriting.** Every task body moved with the rename untouched —
the same rule D96 states for decisions, for the same reason. Only the
file-level pointer paragraphs (provenance, and cross-references to a sibling
file) and the three indexes' own range tables, now section tables, changed.
ID numbers — `A11`, `A46`, `W2`, `O27` and the rest — never do.

**What D95 keeps.** Its measured figures (`PLAN-NOW.md` 2,211 → 58 lines) are
frozen history and stay exactly as written — this entry corrects the
mechanism, not the record. Its "moving is not rewriting," "IDs never change"
and "a task closes by moving to the archive" rulings are untouched; D96
already established that retiring a naming bucket does not disturb the
rulings that never depended on it.
