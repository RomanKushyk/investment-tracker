## D125 — The count is required everywhere, not just where it is typed (2026-09-01)

[`D124`](D124.md) required the count at the form and left the other three doors
open, on the reasoning that the form is where rows are written. That reasoning
had a hole, and a code review found it the same day: **the form is not the app's
only writer.**

`CouponDueCard` builds a `reinvest` and hands it to `recordTransaction`
directly. It never touches `transactionSchema`, so D124's guard never ran on it
— and a `reinvest` moves a position. One press of "also record a reinvest" made
its asset permanently uncountable, which under [`D119`](D119.md) collapses every
coupon figure the asset produces to «—» with nothing saying why.

## The three doors

| door | rule |
| --- | --- |
| `transactionSchema` | a moving row must carry a count (D124) |
| JSON backup row | **the same rule, this decision** |
| `transaction_quantity_required_ck` | **the same rule, this decision** |

`unitPrice` keeps only the one-way rule. It is derivable from
`amount / quantity`, so a row without it loses nothing; a row without the COUNT
cannot be valued or scaled at all.

## The coupon card asks

The card receives `asset`, `due`, `prefill`, `schedule` — **and no price**. It
holds ₴ and cannot turn that into a count without inventing one. So it does what
every other writer does: a units field, revealed with the reinvest checkbox and
required while it is on.

## The seed gained seven counts

| row | asset | count |
| --- | --- | --- |
| `b1` | REIT | 6164 |
| `b2` | Energy | 6000 |
| `b3` | OVDP …8976 | 15 |
| `b4` | OVDP …6475 | 4 |
| `r1` | OVDP …6475 | 0,2192 |
| `r2` | REIT | 43,4835 |
| `r3` | REIT | 61,6161 |

Not decoration — **without them the app exports a demo backup it cannot
re-import**, which is worse than any legacy-file break. `unitPrice` was left off
deliberately: no 4-decimal price reproduces `64 628,62` from 6164, and `amount`
is the authoritative figure.

Measured after adding them: **all 1312 tests still passed.** No pinned figure
moved, because the seed's bonds carry `couponAmount` and no rate, so
`couponPerPayment` never reaches the units.

## The export re-reads its own output

Requiring the count at the importer opened a hole the seed counts do not close:
`buildBackup` validates nothing, so a store created **before** this branch —
pre-#31 rows whose counts are unrecoverable — exports a `formatVersion: 4` file
that passes the version gate and then fails row by row. The owner's only restore
path (D12), unusable, and discovered at the one moment it mattered.

`useBackupDownload` now parses what it just built, through the very reader that
will read it back, and refuses to offer a file that comes back rejected —
naming how many transactions need counts. **A backup nobody can restore is worse
than no backup.**

Checking the whole envelope rather than that one rule is deliberate: the
invariant worth holding is *never write what you cannot read*, and it outlives
whichever rule breaks it next. `json.test.ts` pins the asymmetry so the guard
reads as necessary rather than defensive.

## The DDL check is a deliberate migration break

D112 declined this because pre-#31 counts are unrecoverable
(`w7-migration-translations.md` §4). That is still true — it stops being a
permission and becomes a **sequencing requirement**: the W7 backfill runs
*before* that table takes the owner's history, not after. Owner's ruling, on
[`D113`](D113.md)'s standing grounds — no live users, and their own data can be
re-entered.

The store must not be weaker than the app. That is the argument
`transaction_unit_price_absent_ck` already makes beside it.

## Version 4

The first bump for a **stricter reader** rather than a new field.
[`D122`](D122.md)'s rule covers it unchanged: the version tracks what a build
ACCEPTS. A v3 build accepts a count-less `buy` and a v4 build does not, so every
file written before this is refused — and without the bump that refusal reads
`invalid_type: transactions[3].quantity`, naming a field the owner never omitted
on purpose.

## Supersedes

D124's form-only scope, D122's version literal, and D112's "optional in both
directions and stay that way". D112's REASONING about unrecoverable legacy
counts is untouched and is why the migration sequence matters.
