## D122 — The version tracks what a build accepts (2026-09-01)

[`D113`](D113.md) moved the backup envelope to `formatVersion: 2` when
`quantity` / `unitPrice` landed, and wrote the rule that decides when the number
moves at all. [`D119`](D119.md) adds `Asset.couponRatePct` one branch later, in
the same commit as the form that writes it. The rule applies unchanged.

## Why not reuse 2

The reuse argument is real and worth stating, because it is the reading a later
session will arrive at first:

- `main` still serves a v1 build, so **no production user has ever seen a v2
  file** — the break D113 accepted has not been spent yet.
- 2 and 3 are days apart, on one line of work that was split into two branches
  only for review.
- Nothing on disk anywhere is v2 *and* missing `couponRatePct`… except that it is.

`dev` deploys on every push ([`D67`](D67.md)). A build with `quantity` /
`unitPrice` and no `couponRatePct` was live on dev.quirenote.com between the two
merges — that is what "branch A merged first" means. A backup written by it is a
real file, and reusing 2 would let two deployed builds carry the same version
number and disagree about which fields they accept. That is the one failure a
format version exists to prevent, and it is worse than the refusal it saves:
`unrecognized_keys: couponRatePct` names a field, and the owner has no way to
learn from it that the file is simply older than the app reading it.

**The version tracks what a build ACCEPTS.** Not how much time passed, not how
far the change travelled, not whether production saw it.

## What did not change

`import.ts` never held a literal:

```ts
found > BACKUP_FORMAT_VERSION ? 'newer-format'
  : Number.isInteger(found) && found >= 1 ? 'older-format'
    : 'unsupported-format'
```

so v2 became a named older format by arithmetic, and the fractional / zero /
string cases keep the honest catch-all D113 wrote them for. One test was added
to pin v2 as `older-format` for the same reason D113 pinned v1: a real backup
from an older build must not share a sentence with a hand-edited `0`.

The pinned literals in `json.test.ts` and `import.test.ts` moved by hand and
**stay literals**. A version bump should be a deliberate edit somebody reads in a
diff, not a value a derived expression absorbs silently — which is the whole
point of pinning the envelope shape in the first place.

## Supersedes

D113's version literal (`formatVersion` 2 is current) and its "BUMPED TO 2"
docblock heading. D113's RULING is untouched and is the reason this bump exists:
an optional field pre-declared *before* it ships keeps the version still, and a
field that ships in the same commit as its writer moves it.
