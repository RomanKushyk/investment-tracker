## D55 — The display face is chosen on figures, not on cap-height (2026-08-12)

**Decision:** the display face is **IBM Plex Sans**, superseding the Rubik pick
made hours earlier in D54. `JetBrains Mono` for body is unchanged.

### Why the first answer was wrong

D54 chose Rubik because its cap-height is 0.700 em — identical to Space
Grotesk's. That is a real match and it was the best available criterion *at the
time*, because the comparison had only measured vertical proportions.

Then the **figures** were measured, and they decide it:

| Face | Digits by default | Spread | `tnum`? |
|---|---|---|---|
| **IBM Plex Sans** | **tabular** | **0** | not needed |
| Source Sans 3 | tabular | 0 | not needed |
| Rubik | proportional | 0.208 em | yes |
| Inter | proportional | 0.239 em | yes |
| Golos Text | proportional | 0.135 em | yes |

Verified in a browser rather than only in the font tables: `111111` and `000000`
render at the identical width in IBM Plex Sans immediately, while in Rubik they
are 41.09 px and 60.96 px and only equalise once a call site sets
`font-variant-numeric: tabular-nums`.

**For an app whose every screen is a column of money, "aligned unless someone
forgets a CSS line" is a worse contract than "aligned".** That outweighed the
0.002 em of cap-height Rubik won on. IBM Plex Sans was also drawn for
enterprise data, which is the same reason.

### What the investigation into Inzhur's own typeface found

The provider uses **e-Ukraine** and **e-Ukraine Head** — the typeface made for
Diia — self-hosted, with no monospace face at all (code falls back to
`ui-monospace`).

It was measured as a candidate and **disqualified on the same criterion**:
proportional figures with a 0.2461 em spread and **no `tnum` feature**, so a
column of numbers cannot be aligned with it at all — not by default, and not by
CSS. Confirmed in the browser: `tabular-nums` leaves its digit widths
completely unchanged. Fine for a marketing site with a dozen figures; wrong for
a ledger.

### A measurement error worth remembering

The first pass measured digit widths from the fonts' **Cyrillic** subsets —
which contain no digits at all. Every digit mapped to `.notdef`, all ten came
back the same width, and the result read as "tabular figures" for faces that
have nothing of the kind. It was caught by measuring the **latin** subset of the
same file and getting a different answer.

**A uniform result from a subset that cannot contain the thing being measured is
not a measurement.** Same shape as the green-while-broken family in D53: the
check returned a confident value while testing nothing.
