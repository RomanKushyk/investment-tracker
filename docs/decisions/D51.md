## D51 — The NBU rate is fetched on request, and every failure is an HTTP 200 (2026-08-12)

**Decision:** the hard-coded 44.83 stays as the *stored* value and becomes a
user-owned override. A button fetches the National Bank's official rate and
**offers** it; nothing is applied until the user presses "Use it". Today's rate
only — no archive.

### Why fetching is not an automation

The "exactly one automation" ruling constrains **timers**, not requests. This is
a button, the same shape as "Fetch quotes", and it writes nothing by itself
(G5). Requests are also refused outright in the demo dataset, exactly as the
Inzhur feed is (G4/D16).

No archive, and that is the asymmetry argument from D27 applied in reverse:
NBU's rate history is backfillable by URL at any time, so nothing is lost by not
capturing it. The price archive exists *because* Inzhur's history is not.

### Three things measured, two of which were assumptions worth killing

**Every failure arrives as HTTP 200.** A future date and an unknown currency
both return `[]`. A malformed date returns `[{ Wrong date format }]` — which is
not valid JSON and throws on parse. There is no status code to branch on, so
`parseNbuRate` takes the response **text**, owns the `JSON.parse`, and never
throws. Handing it `response.json()` would have thrown before the tolerant
parser ever ran.

**Weekends and holidays do not 404 and are not empty.** The plan's checkbox said
to determine the behaviour rather than guess it, and guessing would have been
wrong three ways: NBU carries the previous banking day forward. 2026-08-07
(Fri), 08 (Sat) and 09 (Sun) all returned **44.7626**, and `exchangedate` echoes
the date that was *requested*, so the response never admits the value was
carried. That is not a lie to correct — the official rate for a Sunday genuinely
is Friday's — so the UI reports the date the rate applies to and makes no
freshness claim it cannot support.

**`date=` is never optional.** Omitting it returns whatever NBU considers
current, which in the afternoon is already *tomorrow's* rate — a silent
off-by-one on every converted figure on screen.

### The defect the browser caught and the tests could not

Applying the fetched rate updated the store and left the input showing the old
number: `UsdRateField` seeds its draft string once, so a write from outside the
field never reached it. Typecheck passed, 537 tests passed, and the screen
showed 44.83 while the app calculated with 44.866.

The fix was **not** a synchronisation patch. The field now owns the value — the
fetch control takes an `onApply` callback and the field sets its own draft
alongside the store — which removes the class of bug instead of papering over an
instance of it. A second finding from the same pass: the control wrapped onto
its own line and sat flush LEFT while every neighbouring control sits right;
`ml-auto` plus a shorter label fixed it, verified with bounding boxes rather
than by eye, and 360px still has zero horizontal overflow.

**This is the second time in two days that a browser check found what the gates
could not** — the first being nothing at all, because no UI shipped. It is the
argument for the rule, not an exception to it.
