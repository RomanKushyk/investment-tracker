## D101 — W7 ships no foreign keys; the question folds into O33 (2026-08-28)

Owner's ruling, 2026-08-28, closing `PLAN-OPEN.md` **O34**. No `amends`: this
entry APPLIES D100 to reach a ruling and replaces nothing in it, and
`src/decisions/frontMatter.ts` defines `amends` as a scoped amendment whose
reciprocal is derived — claiming one here would report D100 as amended when it
stands untouched. The schema promoted at W7 declares no `FOREIGN KEY`, and integrity stays where
[`../superpowers/specs/data-model/ledger.md`](../superpowers/specs/data-model/ledger.md)
puts it: enforced by the application on write, plus a nightly audit.

**What changed between the question being filed and being answered.** O34 was
filed on 2026-08-27 the day **D99** found that DSQL had grown foreign keys.
For one day it looked dated: an early probe reported that no constraint could
ever be added to an existing table, which would have made W7 the last chance to
declare one. **D100 corrected that** — a key can be added later as
`ALTER TABLE … ADD CONSTRAINT … NOT VALID` — and then went further: drizzle
emits foreign keys as post-hoc `ALTER TABLE … ADD CONSTRAINT` in any case, so a
key declared at W7 arrives `NOT VALID` exactly as one declared years later
would. Declaring now would buy an **earlier** guarantee, never a **stronger**
one. With both the deadline and the advantage gone, the reason to decide in a
hurry went with them.

**Three grounds for the ruling itself, none of them "not yet":**

- **AWS's own guidance points away from the interesting half.** The
  `CREATE TABLE` page says cascading actions count towards the transaction
  modification limit and to "prefer `NO ACTION` or `RESTRICT` for foreign key
  relationships where child-row cardinality is unbounded or unpredictable."
  A user's transactions are unbounded by construction. So the version of this
  feature worth having here is the restraining one, not the cascading one.
- **`RESTRICT` is not free in the client.** `repository.ts`'s `deleteAsset`
  deletes the asset and *then* its transactions — an order a real key would
  refuse. Adopting keys means reversing it, which is a change to live deletion
  code made for a constraint nobody has decided to want.
- **`CASCADE` would answer O33 by side effect.** O33 is choosing between a
  hand-written cascade and tombstones; handing deletion to the database is one
  of those answers, and it should be picked because it is right, not because a
  schema decision arrived first.

**What this does NOT decide.** Whether Quirenote ever uses foreign keys. That
moves into **O33**, which now chooses between the hand-written cascade and
tombstones **knowing that real keys are available** — a third option its row did
not have when it was written. O34's row STAYS in `PLAN-OPEN.md`, rewritten to
point here: that file's own "How an item leaves this file" keeps the Status row
and deletes only the detail section, so the trail from question to decision
survives.

**The cost of waiting, stated so it is not discovered later.** A key added after
the fact is permanently `NOT VALID`: it guards every subsequent write and never
checks the rows that existed when it was added, and `VALIDATE CONSTRAINT` is
refused on DSQL, so it can never be promoted. The rows W7 migrates would
therefore never be verified by the database. **So adopt only behind a clean
integrity audit** — the nightly one the ledger spec already specifies is exactly
the instrument, and its being clean is the precondition that makes the
unvalidated key a formality rather than a hole.

**What stays true and unused.** D99 and D100 measured the shape this schema
would need, and none of it expires: a composite key on the nullable `asset_id`
behaves correctly under `MATCH SIMPLE`, self-referential keys work for
`settles_payout_id`, a late key still cascades, no index is created per key, and
promotion would need a third rewrite rule appending `NOT VALID`. **Every one of
those is written down** — in
[`../../infra/docs/dsql-alter-limits.md`](../../infra/docs/dsql-alter-limits.md)
§ "Foreign keys, measured for the shape THIS schema would need", which is where
O33 reads them. A carry-forward paragraph that only summarised them was this
entry's first draft, and a code review pointed out that three of the five
existed nowhere but here.
