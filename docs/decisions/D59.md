## D59 — Production is a branch, and the domain is what makes that real (2026-08-14)

`quirenote.com` was attached to Amplify on 2026-08-14 and pointed, for about an
hour, at the `dev` branch — the app's only branch at the time. That is the state
this decision replaces.

**Two long-lived branches.** `dev` is the integration base: features branch from
it, squash-merge back, and every push deploys to `dev.quirenote.com`. `main` is
production at `quirenote.com`, and it moves only when `dev` is merged into it —
target at most weekly. The cadence is the point: a production URL that changes on
every commit is a development URL with a nicer name.

**One workflow, not two.** `deploy-frontend.yml` triggers on both branches, takes
the Amplify branch straight from `github.ref_name`, and picks the environment with
`github.ref_name == 'main' && 'prod' || 'dev'`. A second workflow would be the
same file with two words changed, and would drift the first time only one of them
was edited. Concurrency is keyed per branch so a dev push cannot cancel a
production deploy in flight.

**What actually gates production is the GitHub environment, not the branch.** The
IAM trust policy accepts `environment:*` by design (§1.5 of DEPLOYMENT), so the
`sub` claim proves only that the job named SOME environment. The deployment-branch
policy on `prod` — `main` only — is the whole of the restriction. An environment
created without one is trusted the moment it exists.

**The permission policy names both branches rather than `branches/*`.** The doc
predicted this edit ("a new environment that deploys a different Amplify branch
still needs one AWS edit"). Naming them keeps a third branch a deliberate act.

**All three hosts share one CloudFront distribution.** Amplify routes by Host
header, so `dev.quirenote.com` needed one DNS record and one line in the domain
association — no second certificate, because the ACM cert Amplify issues is
`*.quirenote.com` alongside the apex.

**Two documentation drifts surfaced while wiring this**, both now corrected: the
frontend role's inline policy is named `quirenote-frontend-deployPolicy`, not
`quirenote-amplify-deploy` as DEPLOYMENT said, and `gh secret set` does work from
the development machine — the doc's claim that it always 403s was true only of the
work account, which is the one the keyring sometimes makes active.
