## D115 — Measure in chrome-devtools, and calibrate first (2026-09-01)

This repo pins measured figures: [`D56`](D56.md) says to measure the RENDERED
height because `text-[11px]` sets no line height, and `claim-baseline.json`
holds every such figure to a reviewed count. So the figures have to be right,
and on 2026-09-01 a whole branch's worth were not.

### The calibration failure

A code review disagreed with a "measured" 15.4 × 16.9 by 6% in one axis,
computing 15 × 16 from the classes. It was right. The probe that settled it:

```js
const p = document.createElement('div');
p.style.cssText = 'width:100px;height:100px;border:1px solid red;outline:2px solid blue';
document.body.appendChild(p);
getComputedStyle(p).borderTopWidth;  // and outlineWidth, and the rect
```

| | Playwright MCP | chrome-devtools MCP |
|---|---|---|
| `border: 1px` | **0.571px** | 1px |
| `outline: 2px` | **1.714px** | 2px |
| `width: 100px` | 100px | 100px |

`devicePixelRatio` 1, `zoom` 1, root font-size 16 in both. **Lengths are
honest; thicknesses are not.** Anything derived from a box whose size includes a
border therefore came out short — `40 − 2×0.571 − 4 − 4` halves to 15.43 where
the real arithmetic is `40 − 2 − 4 − 4` halving to 15.

It reached a docblock, [`D114`](D114.md), and a WCAG 2.5.8 comparison before the
review caught it. D56's own radius derivation survived only by luck:
`round(15 × 0.26)` and `round(15.4 × 0.26)` are both 4.

### Three more ways a reading lies, all hit the same day

**An animated property, sampled during its transition.** Tailwind's `transition`
utility covers `outline-color`, so a focus ring read 1.00, 13.47 and 13.84 from
the same button depending on when the sample landed. Two of those went into a
comment and a decision as diagnoses. Inject
`*,*::before,*::after{transition:none!important;animation:none!important}`
before reading anything a `transition` utility can touch.

**A background tab.** With `document.visibilityState === 'hidden'` the browser
freezes transitions: `currentTime` stays 0 across a second of wall clock,
`animationend` never fires, and `getBoundingClientRect` returns the pre-flight
value. This was reported as "the animation does not work" and as "the inline
transform is not applied", twice, before `visibilityState` was checked at all.

**Stale CSS.** A live `data-theme` flip, or an HMR update after several edits,
can leave utilities resolving against the previous state — the same class
answered with two different values on two controls on one page. A full reload
costs a second and removes the question.

### The rule

1. Geometry and colour go through the **chrome-devtools MCP**. Playwright stays
   useful for driving a flow; it is not the instrument for a thickness.
2. **Drop the calibration probe first** when a number will be recorded.
3. **Disable transitions** before reading anything animatable.
4. **Check `document.visibilityState`** before believing a motion reading.
5. **Reload rather than flip** `data-theme`, and reload after an HMR burst.
6. When a measurement disagrees with the arithmetic of its own classes,
   **the instrument is wrong until proven otherwise.**

### Why this is a decision and not a note

Because it changes what the ratchets are worth. `claim-baseline.json` exists so
a measured figure is reviewed before it is trusted; a miscalibrated instrument
puts wrong figures through that review with full confidence, and the reviewer
has nothing to compare them against except the arithmetic — which is exactly how
this one was caught, one branch late.
