## D108 — The Issues views, the Project, and the workflows (2026-08-28)

Owner's rulings, 2026-08-28, the same session as [`D104`](D104.md), which records
the wiki and Dependabot rulings. Split out of it when that entry reached the
200-line diagnostic while still holding three subjects — an append-only file at
the cap cannot take a correction without turning the suite red, which is the one
edit such a file must always be able to receive.

### Two saved views now; a GitHub Project as well, on purpose and ahead of need

**Repository Issues saved views** — public preview since 2026-06-25, pinning to
the issues sidebar generally available since 2026-08-20 — live inside the Issues
tab with no separate surface and no extra token scope. Two exist:

- **Needs sequencing** — the issues carrying no milestone. This is the one that
  earns its place on today's shape: an issue filed from the GitHub app arrives
  with **no milestone set**, so without this view it lands invisibly among the
  ones already in `after-current-plans`. It is the inbox of the inbox, and it
  exists because of how capture works, not because the list is long enough to
  need filtering. **No count is written down here on purpose** — one was, twice,
  and issue #29 arrived the same day and made it wrong.
- **Bugs** — the `bug` label. A short list, and no count here either: **this is
  the class D105 lets preempt the plan order**, so it is worth one click, and
  labelling something a `bug` is a decision about queue position rather than
  tone. A missing capability is an `enhancement` (that taxonomy sent issue #30,
  a CI gap, out of this lane).

**A Project is also wanted, and the owner ruled for it knowing it buys nothing
today** — until the plans are finished nothing is in progress, so a board draws
a single column. The reasoning is that the board's value arrives when issues
start moving, and a board created then, mid-flow, is a board configured in a
hurry. This entry records the choice as deliberate rather than premature so that
a later reader finding an empty board does not "tidy" it away.

**It holds ISSUES ONLY.** A plan task (`A`, `W`, `O`) placed on a board becomes a
second source of truth for state that lives in `git` — precisely what D103
declined to do, and the one way this surface can do harm rather than nothing.

**Its workflows are configured, and one is OFF on purpose.** `Auto-add to
project` is on, so an issue filed from the app reaches the board without anyone
touching it; `Item added to project`, `Item closed` and `Item reopened` keep the
board's Status honest in both directions.

**`Auto-close issue` is DISABLED, and this is the ruling most likely to be
reversed by someone tidying up.** It closes an issue when its card is dragged to
Done — a second way to close, which **bypasses the commit**. This repository
closes an issue with `Closes #N` in the squash-merge, and GitHub then records a
link in both directions. That link is one of the reasons D103 chose GitHub
Issues over a hosted tracker at all; a card dragged to Done would close the work
with nothing pointing at the change that did it. Leaving it off makes the board
reflect state rather than decide it.

The four pull-request workflows stay at their defaults. D73 requires no PR, so
this repository's own work never produces one — **but Dependabot does**, and PR
#28 was open within the hour of security updates being switched on.

**The "issues only" rule is enforced by the auto-add FILTER, narrowed to
`is:issue` on 2026-08-28.** GitHub's default for that workflow is
`is:issue,pr is:open`, and leaving it would have put the next Dependabot PR on
the board. The board holding 27 issues and no pull request **at creation time** proved nothing about
it: the board was created `2026-08-28T00:18:59Z` and PR #28 opened
`2026-08-27T23:51:48Z`, twenty-seven minutes earlier, so auto-add had never seen
a pull request at all.

**This is the one setting here that no API can confirm.** `ProjectV2Workflow`
exposes eight fields — `createdAt, enabled, fullDatabaseId, id, name, number,
project, updatedAt` — and **not one of them carries the filter or the action**,
so a workflow can be seen to exist and to be on, never to be doing the right
thing. It was narrowed and read back in the UI, and it is written down here
because a test cannot be made to catch it drifting.

`Auto-archive items` is off; there is nothing closed to archive yet.

**No workflow sets the milestone, and none should.** A Projects workflow cannot:
the project's `Milestone` field has `dataType: MILESTONE`, a mirror of the
issue's own state, and "Set value of a field" writes only custom fields — of
which `Status` is the sole writable one here. A GitHub Actions workflow could,
on `issues: opened`, and it was declined.

**The milestone means "I read this and decided it waits".** Setting it
automatically would make it mean "the issue exists", and three things follow:
`Needs sequencing` would be permanently empty, which reads as *all clear*
rather than *not looked at* and is worse than not having the view; the only
triage point would vanish — the one where a `bug` is recognised as able to
preempt the queue, and where a duplicate is closed as one; and the thing being
automated would be judgement, not toil. There is no toil here: roughly one
issue a day, and triage takes seconds.

Noted for whoever proposes it next at a larger size: the board has the same
blind spot, because `Item added to project` gives every new item `Status: Todo`,
so an un-triaged issue looks sequenced there too. The fix then is a `Triage`
status value, not a milestone workflow — at the cost of a second carrier for one
piece of state, kept in step by hand. Declined at an inbox of a few dozen; worth
revisiting at a few hundred.


### What this does not decide

- Whether GitHub Mobile surfaces saved views or Projects at all is untested here.
  Both were reasoned about as web surfaces; capture stays the app, six taps.
- **The two surfaces are not equally checkable, and the difference matters.**
  Saved views have **no API at all** — they exist only in the UI, and nothing
  can detect one being deleted. The **Project is reachable**: the token carries
  the `project` scope as of 2026-08-28, `gh project list --owner RomanKushyk`
  returns it, and `repository.projectsV2` answers over GraphQL — so a check
  that the board still exists and still holds only issues is writable today.
  None is written yet, and that is a gap rather than an impossibility.
