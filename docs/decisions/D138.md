## D138 — the delete order is the fix, and `RESTRICT` stands (2026-09-03)

[D137](D137.md) ruled O33 earlier the same day. **This entry supersedes exactly
one line of it — the referential action — and leaves the rest standing.** It is
a separate entry rather than an edit because the prose of a decision may never
be rewritten (`RULES.md`), and because the mistake is worth keeping legible.

## What D137 got wrong

D137 changed the owner's `RESTRICT` to `NO ACTION` on this reasoning:

> `RESTRICT` is checked immediately, per row; `NO ACTION` defers to the end of
> the statement. … a `tax` row settling a payout carries the same `asset_id` as
> the payout … so both rows are removed by the **one**
> `DELETE FROM transaction WHERE asset_id = $1`.

**Two things are wrong with it, and a review MEASURED the deeper one.**

**First, "the one `DELETE`" is false in D137's own ruling.** The same entry
requires that delete to be batched — *"Both child deletes are batched, and the
first draft batched only one"* — so it is many statements. A payout in batch 1
with its settling `tax` row in batch 2 fails at the end of batch 1, and the
asset is permanently undeletable: **precisely the failure `NO ACTION` was
adopted to prevent.**

**Second, and this retires the premise rather than the conclusion: `RESTRICT`
never refused the same-statement case at all.** Probed in this repo's own
PGlite (Postgres 18.3), composite self-referential key, both actions:

```
RESTRICT   single-statement DELETE removing payout + its tax : SUCCEEDED
NO ACTION  single-statement DELETE removing payout + its tax : SUCCEEDED
RESTRICT   parent-first, two statements                      : FAILED 23001
NO ACTION  parent-first, two statements                      : FAILED 23503
```

**PostgreSQL implements `RESTRICT` as a non-deferrable AFTER-ROW trigger that
fires at end of STATEMENT — the same moment as `NO ACTION`.** What separates
them is deferrability *across statements in a transaction*, not behaviour within
one. So D137's per-row reading was wrong, its rescue solved a problem that did
not exist, **and the batching objection above is the reason the ORDER matters —
not the action.** The measurement also confirms this entry's own step 1: the
parent-first case fails under *both* actions, which is exactly what nulling the
links first prevents.

The two halves of D137 were written minutes apart while fixing two separate
review findings, and each is correct alone. Together they are not.

## The fix is the ORDER, and it dissolves the question

`transaction_settles_ck` (`infra/schema/user.ts`) is
`settles_payout_id IS NULL OR type = 'tax'` — **only a `tax` row can settle
anything.** So the referencing set is nameable and can be emptied first:

```
-- $1 = user_id   $2 = asset_id   $3 = batch size
-- every step is USER-SCOPED; each BATCH is its own TRANSACTION;
-- each step repeats until a batch affects 0 rows
1. UPDATE transaction SET settles_payout_id = NULL
    WHERE (user_id, id) IN (
      SELECT user_id, id FROM transaction
       WHERE user_id = $1
         AND settles_payout_id IN (SELECT id FROM transaction
                                    WHERE user_id = $1 AND asset_id = $2)
       LIMIT $3)
2. DELETE FROM transaction WHERE (user_id, id) IN (
      SELECT user_id, id FROM transaction
       WHERE user_id = $1 AND asset_id = $2 LIMIT $3)
3. DELETE FROM user_price WHERE (user_id, asset_id, as_of) IN (
      SELECT user_id, asset_id, as_of FROM user_price
       WHERE user_id = $1 AND asset_id = $2 LIMIT $3)
4. DELETE FROM asset WHERE user_id = $1 AND id = $2
```

**Two things about that SQL are load-bearing, and a draft of this entry got both
wrong by writing `LOOP` in front of a bare statement.**

**Each batch COMMITS ON ITS OWN, and saying so is not pedantry.** DSQL's ceiling
is *per transaction* — *"3 000 mutated rows / 10 MiB / 5 min"* — so a loop that
repeats inside one transaction is a no-op against it: all 3 650 `user_price`
rows still accumulate in the same transaction and it fails at commit. **The
batch is the transaction.** D137's *"parent last is what makes it resumable"*
implies this and never says it, which is the half that would have been
discovered at implementation.

**Postgres — and so DSQL — accepts no `LIMIT` on `UPDATE` or `DELETE`.** Written
as `LOOP UPDATE … WHERE …`, each step is *one* statement over the whole set,
which blows the 3 000-row ceiling that is the only reason batching exists. The
batch has to be expressed as a key-set sub-select, which is what the block above
does; the loop then repeats the same statement until it reports zero rows.
**D137's original defect was a step whose batching was assumed rather than
written, and assuming it twice would be the same mistake.**

**Every predicate is scoped by `user_id`.** `transaction`'s primary key is
`(user_id, id)` and `asset`'s is `(user_id, id)` — **`id` is unique only within
a user** — so `settles_payout_id IN (SELECT id FROM transaction WHERE
asset_id = $1)` without `user_id` can reach another tenant's rows and NULL their
settlement links. This file's own schema makes the same argument about
`transaction_settles_uq`: *"USER-SCOPED. An unqualified `UNIQUE(settles_payout_id)`
would constrain half a key."*

**Step 1 NULLS the link; it does not delete the row.** Two earlier drafts of
this entry deleted instead, and each was wrong in its own way — both are kept
here because the second mistake was made while fixing the first.

**Draft 1 — `WHERE asset_id = $1 AND settles_payout_id IS NOT NULL`.** Nothing
in the schema ties a settling row's `asset_id` to the settled payout's:
`transaction_settles_ck` is only `settles_payout_id IS NULL OR type = 'tax'`.
So a `tax` on asset **B** — or one carrying no asset — may settle asset **A**'s
payout, and would never be in `WHERE asset_id = $1`. Loop 2 then deletes A's
payout under a live reference and raises `23503` **permanently**. (Every SQLSTATE in this entry is DSQL's, which is the engine W7 ships on; Postgres raises `23001` for a `RESTRICT` refusal — see the divergence noted below.)

**Draft 2 — `DELETE … WHERE settles_payout_id IN (SELECT …)`.** It closes that
hole and opens two more:

- **Chains.** `transaction_settles_ck` constrains the SETTLING row's type, never
  the SETTLED row's, so a `tax` settling a `tax` is schema-legal and
  `transaction_settles_uq` forbids only two rows settling the same target, not a
  chain. With the step batched, `T1` in batch 1 and `T2`-settles-`T1` in batch 2
  is `23503` again. **That is the very error this entry convicts D137 of** —
  reasoning from domain intent where the argument is about what the schema
  permits.
- **Collateral deletion.** The predicate's whole point is that it reaches rows
  belonging to OTHER assets, so deleting asset A would destroy a `tax`
  transaction filed against asset B and move B's figures. **That is issue #34's
  shape exactly** — a row destroyed because it merely carried a reference — and
  this project has that bug on record already.

**Nulling the link has neither problem, and needs no FIXED-POINT loop** — it still batches, and step 1 repeats until a batch affects zero rows like every other step; what it does not need is a second pass to catch a deeper layer. An
`UPDATE` removes references without removing rows, so batching cannot strand a
chain. **Stated precisely, because a draft of this sentence over-generalised in
exactly the way this entry convicts D137 of:** step 1 nulls every row that
settles one of asset A's transactions — it does NOT null rows further out. A
`T3` settling a `T2` that belongs to asset **B** keeps its link, and does not
need to lose it, because `T2` is not asset A's and step 2 never deletes it.
**What holds is the property that matters: nothing references anything step 2
will delete.** Rows belonging
to the asset are deleted by step 2 regardless; rows belonging elsewhere survive
with their amount intact and only the settlement link gone, **which is the thing
that actually died with the payout**. `NULL` satisfies
`transaction_settles_ck` unconditionally, so no constraint objects.

After step 1, **both `RESTRICT` and `NO ACTION` pass.**

**One accepted cost, named rather than left to be found.** Because each batch
commits, step 1 permanently changes rows belonging to OTHER assets before
anything is deleted. A run abandoned after step 1 leaves asset B's `tax` rows
with their settlement links gone while asset A still exists — a write with no
delete to justify it, and nothing records that it happened. It is defensible:
the link is the only thing lost, the amount and the row survive, and the
alternative (deleting those rows) is the issue-#34 shape rejected above. But it
is the one step in a resumable procedure that is not itself reversible, and
whoever builds the confirmation dialog should know that.

**A second cost, and it constrains how a retry is written.** The procedure is
deliberately non-atomic, so *"after step 1 nothing references anything step 2
will delete"* holds **only in the absence of a concurrent write**. A `tax` row
inserted between step 1's final batch and step 2 re-creates a live reference and
step 2 raises `23503`. That is recoverable — but only if the retry **restarts at
step 1**. An implementation that resumes at the failed step, which D137's
*"a failure midway is resumable"* invites, would retry step 2 forever. **Resume
means resume the SEQUENCE, not the step.**

**Two reads are unindexed, and both are the ones keyed on `asset_id`.** Step 1's
outer predicate is served by `unique(user_id, settles_payout_id)` and step 3 by
`user_price`'s PK prefix; step 1's inner `WHERE asset_id = $1` and step 2 are
not. `transaction` carries `primaryKey(user_id, id)`, `index(user_id, date)`
and `unique(user_id, settles_payout_id)` — so
`WHERE user_id = $u AND settles_payout_id IN (…)` is served by that unique,
while **nothing indexes `asset_id`**, which leaves step 1's inner
`WHERE asset_id = $1` and step 2 scanning the user's rows.

**And there is a third scan the procedure does not issue: `RESTRICT`'s own.**
`infra/docs/dsql-alter-limits.md` records that **no index is created per foreign
key**, so step 4's `DELETE FROM asset` makes the cluster verify nothing still
points at it. **That cost is asymmetric**: the `user_price` check is served by
that table's own primary key, `(user_id, asset_id, as_of)`, whose leftmost prefix
is exactly the referencing pair — but the `transaction` check has no index and
scans. It runs on every asset delete, and it is the cost the key charges for the
guarantee. At this data size the two scans are fine; A50's recorded
full-scan threshold is the thing to re-read if they stop being.

## So the action is decided by evidence, not by semantics

With correctness no longer turning on the choice, the question becomes which
action this project has actually **measured on DSQL**:

| Action | Probed? |
|---|---|
| `ON DELETE CASCADE` | **yes** — `infra/docs/dsql-alter-limits.md`, foreign-key section |
| `ON DELETE RESTRICT` | **yes, but INLINE only** — probed as a `CONSTRAINT … ON DELETE RESTRICT` inside a `CREATE TABLE`, never on a late `NOT VALID` key |
| `ON DELETE NO ACTION` | **NO. Never probed.** |

Measured 2026-09-03, and stated precisely because a first draft of this line
overstated it: `NO ACTION` was **never probed against the cluster**. It is not
absent from `infra/docs/` — `dsql-alter-limits.md` records it once, in drizzle's
generated output (`ON DELETE no action ON UPDATE no action`), and that page says
of the statement that it *"was read, never executed"*. A default in generated
text is not a measurement.

**And that occurrence carries a hazard this ruling must name: `no action` is
drizzle's DEFAULT.** So W7 has to set the action explicitly on every key, or the
generated `ADD CONSTRAINT` silently ships the action D137 chose and this entry
supersedes. **And ONE API form serves all six** — checked against the installed drizzle:
`foreignKey({ name, columns, foreignColumns }).onDelete('restrict')`, table-level.
The column-level `references(ref, actions?)` is single-column, so it cannot
express four of them at all — and it is ruled out for the other two as well,
because it has **no `name` slot**, so drizzle would derive a name and break
`user.ts`'s rule that constraint names match the generated SQL. Four are
composite because **four of the six keys here are composite** (contract 3
leads each per-user PK with `user_id`; the two single-column ones are
`account.user_id → app_user.user_id` and `asset.user_id → app_user.user_id`),
so those four must be
`foreignKey({ columns, foreignColumns }).onDelete('restrict')` — with the action
**chained**, since `foreignKey()`'s config takes only
`name`/`columns`/`foreignColumns`. A single-column `references(() => asset.id)`
emits a reference to `asset("id")`, which carries no unique constraint, and the
cluster rejects it `42830`. **`CLAUDE.md`'s measure-first rule and
[D115](D115.md) both say an unverified figure must not pass as a reviewed one**,
and D137 made an unprobed referential action binding in three documents at once
while depending on its end-of-statement timing — the subtler half of its
behaviour.

**One consistency this entry owes its own argument.** It rejects `NO ACTION` as
unprobed — and the batching form above, the row-constructor
`WHERE (user_id, id) IN (SELECT … LIMIT $n)`, is **also unprobed on DSQL**. It
is valid Postgres, but so is `ON DELETE NO ACTION`, and
`infra/docs/dsql-alter-limits.md` exists precisely because DSQL's subset
diverges. **The difference is what each one costs if wrong**: an unprobed
referential action is a silent contract that fails only on the one delete path
that trips it, while an unprobed statement form fails loudly the first time it
runs. Both should be probed, and **W7 owes a round on the batching form** —
recorded here so it is not discovered at promotion.

**And the refusal's SQLSTATE differs by engine — record it before anything
handles it.** The probe above gives `RESTRICT` → **`23001`**
(`ERRCODE_RESTRICT_VIOLATION`) and `NO ACTION` → `23503` on Postgres, while
`infra/docs/dsql-ddl-first-contact.md` records **DSQL returning `23503`** for a
delete against an `ON DELETE RESTRICT` key. **So error handling keyed on `23503`
matches on the cluster and misses in a local PGlite test**, and any code or test
that branches on the code must say which engine it means.

**A qualification this entry owes its own standard, found by review.** The
tiebreaker is *`RESTRICT` was measured and `NO ACTION` was not* — and `RESTRICT`
was measured **inline**, inside a `CREATE TABLE`, while W7 ships a post-hoc
`ALTER TABLE … ADD CONSTRAINT … NOT VALID`. The `CASCADE` bullet on the same
page qualifies itself with *"including on a key added late as `NOT VALID`"*; the
`RESTRICT` bullet does not. **So the shape W7 actually ships is unprobed for
both actions**, and the tiebreaker is weaker than *measured against unmeasured*:
it is *measured in a neighbouring shape against measured nowhere at all*. It
still points the same way, and **W7's owed probe now covers `RESTRICT` as
`NOT VALID`** rather than only the batching form.

**So `RESTRICT` stands: it is the better-measured action, and it is what the
owner said.** *(AWS's guidance is deliberately NOT offered as a third reason — it
names `NO ACTION` and `RESTRICT` together, as D137's own table says, so it
discriminates between them not at all. It ruled out `CASCADE` and nothing
else.)* The correction
D137 recorded against the owner's word is itself withdrawn.

## What is NOT superseded

Everything else in D137 holds, and none of it depended on the action:

- the **batched application cascade**, children first and the parent last, so a
  failure midway is resumable (this entry adds the link-nulling step in front of
  it and changes nothing else about the order);
- **`CASCADE` rejected** — AWS's guidance that cascading actions count towards
  the transaction modification limit, against DSQL's 3 000 mutated rows and a
  `user_price` grain of one row per asset per date;
- **tombstones rejected**;
- **[D101](D101.md) amended** — W7 does take foreign keys;
- the **third promotion rewrite rule** (append `NOT VALID`).

**One thing D137 listed as an open gap is CLOSED here, and its prescribed remedy
was wrong.** D137 named a `tax` with `asset_id IS NULL` settling a payout that
has one, and asked W7's schema task for *"a CHECK mirroring the domain's
`targetsAsset`"*. That CHECK cannot work: `targetsAsset('tax')` is **`true`**
(`PORTFOLIO_LEVEL` is `deposit`/`withdrawal` only), so it would force a tax row
to carry *some* asset and never the *same* one — leaving the asset-**B**-settles-
asset-**A** case untouched. **Step 1's `settles_payout_id IN (…)` predicate
closes both cases without any schema change**, which is why no CHECK is owed.

**And one gap this entry OPENS, named rather than left implicit.** Enumerating
the keys turned up two that neither entry had mentioned:
`transaction.(user_id, account_id) → account.(user_id, id)`, and
`asset.user_id → app_user.user_id` — `asset` is the one per-user table whose
`user_id` anchors to nothing, since `transaction` reaches `app_user` through
`account` and `user_price` through `asset`. This ruling covers
the **asset** cascade only. What deleting an ACCOUNT must do to the transactions
filed against it is unruled — under `RESTRICT` it simply refuses until they are
gone, which is a safe default rather than an answer. It joins the user-delete
question D137 left with W8.

**Both that and `transaction.delete`'s new refusal are now registered as
`PLAN-OPEN.md` O36**, and the reason they had to be is worth keeping: a review
found them recorded only in a contract table cell and in this entry — so a
reader of the file this project designates as the register of open questions
would have seen deletion as fully closed.

## The pinned `deleteAsset` rule, and why neither entry touches it

**Raised by a code review as a conflict, ruled by the owner 2026-09-03 as no
conflict at all** — recorded here because two earlier reviews read past it and
the third read it as a contradiction, and a reading nobody wrote down gets
re-litigated.

[`NEXT-PHASE-PLAN.md`](../plans/NEXT-PHASE-PLAN.md) pins:

> **G2's `deleteAsset`** — assets accumulate, nothing is deleted. **The method
> stays in the codebase** (it is tested and harmless) but **no new surface** may
> depend on cascade-delete semantics.

**Both halves matter and the first is usually skipped.** The rule *keeps* the
method; what it forbids is a new dependent. **`asset.delete` at W7 is not one**
— it is the portfolio dialog's existing button over HTTP instead of Dexie: the
same capability, reached the same way, on the same asset. W7 creates no
dependent that does not exist today.

**But "the same CONFIRMATION" would be false, and the dialog owes one line.**
`cascadeCounts` (`screens/portfolio/portfolio.ts`, called at
`AssetDialogs.tsx:48`) counts only the target asset's transactions and snapshot
days. Step 1 also nulls settlement links on rows belonging to **other** assets —
the accepted cost above — and nothing in today's confirmation says so. Porting
the dialog verbatim would ship that silence.

**What WOULD be a new surface is a delete control on the DB browser's assets
tab**, and `phase-w-iv-v.md`'s W14 forbids exactly that. The asymmetry is
deliberate and survives this ruling: **the browser deletes ROWS — a transaction,
a snapshot — and the portfolio deletes an ENTITY that owns rows.** Removing one
transaction costs one row; removing an asset from a table view costs a year of
history behind an affordance that looks identical to its neighbours.

**The weak point, stated:** once the op exists in the API, W14 *could* call it,
so the rule now rests on W14's discipline rather than on the op's absence. That
is true of every op, and the rule speaks of product surfaces rather than API
minimalism — but a reader who wants it enforced rather than promised should make
W14's exception a test.

## The procedural lesson, stated because it caused this

**D137's defect was introduced while fixing a code-review finding, and survived
because the branch merged without a second review pass.** Both halves — "batch
the transaction delete too" and "use `NO ACTION`" — were review fixes; the
review that requested them could not see them, and nothing looked at the pair.

Two other instances of the same shape were found the same day by an audit:
D134's *"repeated in seven places"* left above a table a review fix had grown to
eight, and `section-r.md`'s *"these are the three tests"* above four checkboxes.
**All three were created by review fixes and caught by nothing.**

**[D134](D134.md)'s count is corrected HERE, not there, and that is the rule
working.** Its body still reads *"repeated in seven places"*; the table beneath
it holds **eight**, `maxLength={2}` being the eighth, and D134's own front-matter
summary already says eight. A first attempt struck the word through in D134's
body — `RULES.md` allows a `summary` fix as metadata and says *"the prose under
the heading is what may never change"*, and every other strikethrough in this
folder is in front matter. So the edit was reverted and the correction lives
where corrections belong: in a later entry. `section-r.md` is a plan file, not a
decision, and was simply fixed. A second pass
on a branch whose fixes were substantive is what closes it, and this entry is
the evidence that it is worth the cost.
