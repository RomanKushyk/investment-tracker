## D97

**A50's re-plan: the alias changed a sort node and nothing else, at every range
width tested — and it took four rounds because the first three inferred
(2026-08-26)**

A50 named the shadowed column in `observeNbu`'s newest-capture-per-date query
and in `diagnose`'s `price_observation` sample, then re-planned against the live
cluster. Working: `infra/docs/replan-a50.md`.

**What is measured.** `price_capture` at 6,666 rows, 3,867 of them
`source='nbu_fv' AND ok`.

*Plan shape by range width, both forms, `EXPLAIN (VERBOSE)`:*

| Range | aliased | qualified |
|---|---|---|
| 7d – 1500d | `Sort` over **Index Scan `price_capture_as_of`** | `Incremental Sort` over the **same Index Scan** |
| 2000d – 3900d | `Sort` over **Full Scan (btree-table)** | `Sort` over the **same Full Scan** |

**The alias never changed the scan.** At every width tested both forms pick the
same access path, and both fall to a `Full Scan` between 1500 and 2000 days. The
only difference the fix makes is `Sort` → `Incremental Sort` with
`Presorted Key: price_capture.as_of` — which does settle that DSQL serves a
mixed-direction order (`as_of` ASC, `requested_at` DESC) from an ASC/ASC index,
the standing question, but a sort node is not what this query is billed for.

*Cost, warm medians over four alternated runs, 7-day window:*

| Form | Compute | Read | Total | Exec |
|---|---|---|---|---|
| aliased | 0.00177 | 0.25418 | 0.25594 | 1.414 ms |
| qualified | 0.00181 | 0.25418 | 0.25599 | 1.454 ms |

Indistinguishable, the qualified form marginally the slower; per-run compute
spans overlap completely (0.00168–0.00189 against 0.00171–0.00189). Read is
**99.3%** of the total and identical to five digits in every run.

**So A50 removed a defect, not a cost.** Worth doing — the alias-shadowing class
cost 64.989 DPU against 9.508 once already, on a query whose `LIMIT 60` the alias
was disabling (D91) — but on *this* query it buys nothing at any width, and that
is now measured rather than assumed.

**D91's 0.356 DPU is not reproducible, and the cause is UNKNOWN.** Measured on
D91's own window (`2026-08-18 .. 2026-08-25`), warm, three runs: **0.26343 read,
0.26528 total, identical for both forms** — 34% below 0.356. Warmup does not
explain it: cold-to-warm moves Read by 0.55% and Read is almost all of the total.
Window content does not explain it: that window holds 6 rows and 27.2 KiB against
the 7-day window's 5 and 22.7 KiB, and it was measured directly anyway. Query
form does not explain it: both forms return the same figure. **State it as
unreproduced, not as superseded-because-warmup.** The same caution applies to
**64.979**, the open-range figure from the same D91 session: it has not been
re-measured here — executing that branch is what it costs — so it is one cold
sample too, and it is load-bearing for keeping `price_capture_as_of`.

**What that leaves for O32.** A date-range bound is viable and now has a
measured ceiling: anywhere up to ~1500 days keeps the plan on
`price_capture_as_of`. What it does *not* have is a way to keep the current
pagination contract — `observeNbu` derives `complete: !remaining` and `nextFrom`
from `captures.length > dates`, i.e. from the JS limit having truncated the
fetch, so capping the range in SQL makes a partial run report `complete: true,
nextFrom: null` and the caller stops believing the archive is derived. A plain
SQL `LIMIT` is ruled out separately: the recorded open-range plan puts a `Sort`
above the `Full Scan`, and a `Sort` consumes its whole input before it yields a
row.

**The lesson, and it is the reason this entry is long.** *One `EXPLAIN (ANALYZE)`
is not a measurement, and a plan you did not run is not evidence.* Four rounds:
round 1 reported a 9.1× compute win that was first-parse warmup — the tell was a
50× planning-time gap between two near-identical statements, sitting in the same
table. Round 2 fixed the method and then attributed D91's gap to warmup, which
its own numbers refuted. Round 3 measured the widths that round 2 had declared
out of scope, and they inverted the framing: the interesting question was never
"how much cheaper" but "does the scan path ever differ" — it does not. Every one
of those errors was caught by review, none by a test, and the cluster that
answered each of them was reachable the whole time.
