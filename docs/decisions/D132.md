## D132 — The archive writes every day, and O5's remainder cost no column (2026-09-02)

`PLAN-NOW.md`'s Section Q says W4's first act is to **ask**, not to write DDL.
Two questions, both answered before any code.

### 1. Write-every-day, not write-on-change

W3 left this open deliberately and said so: *"the funds ARE in every Sunday
payload with an unchanged NAV, so W4 must choose … The key supports both."*

**Ruled: write every day.** Three grounds, and the first two were already
binding contracts rather than fresh arguments:

- [`price-archive.md`](../superpowers/specs/data-model/price-archive.md) defines
  the table as *"per instrument per capture — exactly what the provider
  served."*
- Its governing rule for consumers is *"levels carry forward; changes never do.
  **A zero delta and an unknown delta must never render the same.**"*
  Write-on-change does not make that distinction hard to render — it removes it
  from the data. A fund with no row on Sunday is byte-identical to a fund whose
  capture never ran.
- The cost is ~260 redundant fund rows a year, against storage that reaches
  1 GB in roughly 657 years and ~173 DPU/month against a 100,000 allowance.

The alternative's real price was never the rows: it was that **every
completeness check would have to know, for ever, that five funds are
legitimately absent two days a week.** A calendar rule embedded in each reader
is the kind of thing that is true when written and silently wrong after the
first listing change.

### 2. `NOT NULL` where certain — and the schema had already done it

D100 measured what DSQL can alter later: a nullable column, a
`CHECK … NOT VALID` and a `DEFAULT` can all be added; **`NOT NULL` and a type
change cannot.** So only those two were ever at stake.

**Ruled: pin `NOT NULL` where the value is certain, nullable where the
instrument class decides.** Applying it produced no work at all:
`price`, `observed_at` and `parser_version` are already `NOT NULL`;
`return_rate_buy`, `return_rate_sell` and `status` are already nullable, which
is right because only bonds have them.

**So O5's remainder resolves to "no new non-key column is needed", and
`price_observation` takes no DDL in W4.** `basis` has accepted
`buy`/`sell`/`nav` since row one for exactly this day. The irreversible half of
this phase was spent correctly by A4 a month before the phase began — which is
what the evidence gate was for.

### What the implementation found that neither ruling anticipated

**`nav: 0` is the provider's NULL, and it nearly reached the archive.**
[`D31`](D31.md) measured it for funds — *"it is exactly `0` for `ocean-plaza`
and `zhytniy`"* — and that is why fund value uses `sell`. The fixture shows
every **bond** carrying `"nav": 0` as well: a bond has no net asset value, and
the feed fills the field rather than omitting it.

The first mapping wrote a `nav` row whenever the field was present, which would
have put **a permanent ₴0 NAV on every bond-day** in a table whose role holds
`SELECT, INSERT` and no `DELETE`. Caught by a test against the real fixture, not
by reading. A sentinel is not a measurement, and storing one breaks the same
zero-versus-unknown rule that decided question 1 — in the writer this time.

**Deliberately not generalised.** Only `nav` has the evidence. W3 watched
`UA4000239016`'s two-sided quote collapse to a zero **spread**, which is a real
observation that must survive, so a blanket "zero means absent" would have
destroyed it.

### Two things already built that this made wrong

- **`ObservationsWritten` is dimensioned by source.** Its own rationale is that
  *"flat through a working week means the derivation stopped"* — true of one
  source at a time. Undimensioned, Inzhur's daily rows fill in NBU's weekend
  zeros and a dead NBU observer reads as healthy.
- **`diagnose`'s reconciliation took its source from the literal `'nbu_fv'`.**
  Harmless while the table held one source; silently wrong with two, because it
  would measure every Inzhur ref against NBU's publication calendar — closed at
  weekends, where Inzhur is not — and report a two-day gap every week that does
  not exist.

### Scope: wide for Inzhur, narrow for NBU

`ObserveRequest.refs` argues in writing that **narrow is the safe direction**,
because the archive has no `DELETE` grant and starting wide means deleting rows
3,000 at a time. For a 185-instrument national file whose readers want two of
them, that is right.

Inzhur goes the other way, on [`D72`](D72.md): what the daily capture buys is
*"the Inzhur dealer quote **for every instrument**, which exists nowhere else."*
Narrowing it would discard the reason the capture exists. The set is also two
orders smaller — 32 bonds and 5 funds — so the argument that refused ~400,000
NBU rows does not reach it.

### Still open, and named rather than assumed

- **The live run has not happened.** The observer and `bond_terms` are written
  and gated; no row has been written to the cluster. The first live
  `{observe:{source:'inzhur'}}` should take a narrow date range, because a
  wrong row cannot be deleted.
- **The instrument counts remain unreconciled.** W3 asked W4 to settle four
  figures that disagree (35 on 08-10, "all 31 bonds" on 08-11, 36 as 31+5 over
  08-12→08-17, 35 as 30+5 on 08-12 and 37 as 32+5 on 08-31). They cannot be
  reconciled from documents alone — the set genuinely grew during the window —
  and inventing a reconciliation would be worse than carrying the question.
- **O32 is untouched.** `observeInzhur` mirrors `observeNbu`'s
  `complete`/`nextFrom` contract, defect included, deliberately: two observers
  with different contracts is worse than one known-imperfect one, and the
  Inzhur window is 21 days rather than 3,900.
