## D135 — the observe window bounds the statement, and completeness names both bounds (2026-09-03)

`PLAN-OPEN.md` **O32** has been open since 2026-08-26, from A50's re-plan
([D97](D97.md)). It asked two things, and both are answered here: how
`complete`/`nextFrom` are re-derived once the statement is the bound, and
whether a manual full re-derive stays possible at all.

## What is actually unbounded today, measured 2026-09-03

**Two bounds exist and only one of them is real.**

- `limit = req.limit ?? 400` (`infra/src/capture.ts:819`) is a **JS** bound. It
  stops the loop — `if (dates >= limit) break` at `:838` — after the rows have
  already arrived.
- **The SQL statement has no bound at all.** `NEWEST_CAPTURE_PER_DATE` selects
  every usable capture in `[from, to]` **with `payload_gzip` projected**.

`NBU_ARCHIVE_START` is `'2016-01-04'` (`:557`), so an open range spans **3 895
calendar days** — and A50's nine-width plan recorded the query holding
`Index Scan using price_capture_as_of` out to 1 500 days and falling to
`Full Scan (btree-table)` by 2 000. **The default run is already past that.**
At roughly 250 published days a year it also fetches about **2 666 rows of
payload in order to consume 400**.

So the cost is two things at once: a full scan, and the payloads of six runs'
worth of dates pulled into Lambda memory to serve one run.

## Why a SQL `LIMIT` is not the fix, and this was already known

[D97](D97.md) recorded it: the open-range plan puts a `Sort` above the scan, and
**a `Sort` consumes its whole input before yielding a row**, so a `LIMIT` above
it bounds the output and not the work. [D91](D91.md)'s `LIMIT 60` worked only
because its input arrived index-ordered. Nothing here re-opens that.

## The ruling, half one — completeness from the two bounds

The statement takes a window:

```
windowEnd = min(to, from + CAP)
```

and the run can now stop short for **two independent reasons**, so the
derivation names both:

| What truncated | `nextFrom` |
|---|---|
| **the JS limit** (`dates >= limit`) — **checked FIRST, and it wins** | `cursor + 1` |
| the window alone (`windowEnd < to`, limit did not bite) | `windowEnd + 1` |
| neither | `null`, and `complete: true` |

Written out: **`complete = windowEnd >= to && dates < limit`**.

**THE PRECEDENCE IS THE RULING, not a detail of it — both bounds truncate on
almost every run.** At CAP 1 000 a window holds ~684 capture dates and the limit
is 400, so a normal invocation satisfies `dates >= limit` **and**
`windowEnd < to` at once. Take the window's answer there and `nextFrom` jumps to
`windowEnd + 1`, **silently skipping the ~284 capture dates in
`(cursor, windowEnd]` that were fetched and never consumed** — and the caller
then reports the archive derived. That is the same defect this ruling exists to
prevent, reached from the other side, and a three-row table that does not say
which row wins is how an implementer arrives at it honestly.

**And the compact spelling is wrong.** `nextFrom = min(cursor, windowEnd) + 1`
looks like it captures this and does not: when the limit did NOT bite, `cursor`
is the last capture date actually seen — `from` itself if the window held none —
so the `min` is `cursor` again and the caller advances by a day across an empty
stretch instead of by CAP. **The two cases are ordered, not combined.**

**Why this replaces what is there.** `remaining = captures.length > dates`
(`:898`) is true only when *SQL returned more rows than JS consumed*. Bound the
range in SQL and SQL returns exactly what JS eats, so a partial run reports
`complete: true, nextFrom: null` and the caller stops **believing the archive is
derived**. That is `RULES.md`'s recurring defect verbatim — a green indicator
that is green because nothing was attempted — and it is the reason O32 exists
rather than being a one-line change.

**It terminates by construction, and that is the property to preserve.** When a
window contains no usable captures at all, `cursor` never moves; deriving
`nextFrom` from the cursor alone would advance the caller by **one day per
invocation** across a gap. Deriving it from `windowEnd` advances by CAP. The
window is monotone toward `to`, so the loop always ends.

## The ruling, half two — the full re-derive survives

**`{observe:{}}` still means the whole archive from `NBU_ARCHIVE_START`.** It is
a loop the caller drives on `nextFrom` — which is what
`ObserveRequest.limit`'s own docblock already says it is: *"The caller loops on
`nextFrom` rather than fighting the Lambda timeout, exactly as the capture
backfill does."*

**And the invocation count does not grow.** At ~2 666 capture dates over the
archive, the JS limit of 400 already forces about seven invocations. A
1 000-day window holds roughly 684 capture dates — more than 400 — so **the JS
limit still bites first** and the window never becomes the binding constraint
except at the tail. The window's job is to bound the *statement*, not the loop.

## Why not ask the database

The obvious alternative — `SELECT EXISTS(… WHERE as_of > cursor AND as_of <= to)`
— reads completeness from the data instead of from our own arithmetic, which is
the shape `RULES.md` generally prefers. **It is rejected here on a termination
hazard.**

`NEWEST_CAPTURE_PER_DATE` filters to **usable** captures —
`ok = true OR ($4::text IS NOT NULL AND error LIKE $4)` (`capture.ts:801`) — and
a probe not carrying the identical predicate reports rows remaining that the
derivation **will never consume**, so `nextFrom` never becomes `null` and the
caller loops forever.

**How strong that hazard is depends on the observer, and this entry's first
draft overstated it for the one the question is about.** `observeNbu` binds
`$4 = null` (`:830`), so **its** predicate is plain `ok = true`; only
`observeInzhur` binds `TRACKED_ABSENT_LIKE` (`:993`) and gets the two-branch
form. So on the NBU path a probe would have to get `ok = true` wrong to loop,
which is a smaller mistake to avoid than the text first claimed. **The rejection
stands on the pair rather than on NBU alone**: the two observers must not
diverge (`:923`), so any probe has to satisfy the harder predicate anyway, and
arithmetic that terminates by construction still beats a predicate that must be
kept in step by hand. Keeping two
predicates in step across a file that already documents *two observers that
drift are two contracts* is a standing cost for no gain over arithmetic that
terminates by construction.

Not rejected forever: if the predicate is ever factored into one shared
fragment that both the fetch and the probe must use, this becomes cheap and
correct at the same time.

## CAP is 1 000 days

Chosen, not measured — the measurement bounds it and does not pick it. A50
planned nine widths: **1 500 days is the last that held the index scan and 2 000
the first that did not**, so the true cliff is somewhere in `(1500, 2000]` and
1 500 is the edge of tested ground rather than a safe value. 1 000 sits clear of
it, and costs nothing: it still holds more capture dates than the JS limit will
consume, so it does not add invocations.

**It is a parameter, not a contract.** Any value that keeps the index scan and
exceeds the limit's reach in capture dates satisfies this ruling; moving it
inside that band needs no decision, and moving it outside needs a measurement.

## Both observers change together

`observeInzhur` (`:954`) **mirrors `observeNbu` on purpose** — the file says so
at `:923`, and says why: *two observers that drift are two contracts, and the
one that drifts is the one nobody re-reads*. It carries the identical
`limit ?? 400` (`:957`), the identical `dates >= limit` break (`:987`) and the
identical `captures.length > dates` (`:1118`).

**It does not need the bound today**, and takes it anyway. `INZHUR_ARCHIVE_START`
is `'2026-08-11'` (`:918`), so its open range is 23 days and stays under a
1 000-day window until 2029. Changing one observer and not the other would buy a
divergence the file exists to prevent, in exchange for nothing.

## What this does not decide

- **The `Sort` itself.** The plan still sorts; this bounds its input rather than
  removing the node. Whether the open range can be made index-ordered end to end
  is a separate question and no one has asked it.
- **`refs` scope.** Still `TRACKED_ISINS` by default, and the narrow-is-safe
  reasoning in `ObserveRequest.refs` is untouched.
- **Anything about `price_capture`'s key or lifecycle** — [D30](D30.md) holds.
