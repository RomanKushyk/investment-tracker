## D103 — The inbox leaves the repository; the plans stay (2026-08-28)

Owner's ruling, 2026-08-28, after three rounds of measurement against the
question "should planning move to a task manager".

### The ruling

**The inbox — raw ideas and bug reports, in the owner's words — lives in GitHub
Issues on this repository**, labelled `enhancement` and `bug`.
`docs/plans/USER-FEATURES-DRAFT.md` and `docs/plans/USER-BUGS-DRAFT.md` are
retired. Their 27 lines became issues #1–#27.

**Everything else stays in `git` and is not up for migration:** `PLAN-NOW.md`,
`PLAN-WAITING.md`, `PLAN-OPEN.md` and their section files, this log, and
`FOLLOW-UPS.md`.

### Why the plans stay — the measurements that decided it

- **57% of commits touching `docs/plans` change `src/` or `infra/` in the SAME
  commit** (62 of 108, over 301 commits). Today one commit is one revert. A
  hosted tracker splits every one of those into a `git` half and a tracker half
  that cannot be reverted together — which is what D73 makes the branch the
  unit of.
- **139 machine-checked claims live inside the plan files**, of 2595 in
  `claim-baseline.json`, plus 3 fact fences and 4 line-cap entries. Migrating
  them means either a red `pnpm test` or deleting the checks.
- **D76 reviews documentation by diff, and that is the point.** A hosted store
  has no diff, so the review that this repository's evidence came from could not
  run at all.
- Density: 241 backticked code paths and 290 `D<n>` citations inside the plans;
  42 of 102 decisions cite the plans back; 120 of 206 `src/` files cite a
  decision inline. Removing `docs/plans` would have meant editing 143 files and
  rewriting 412 references.
- Content shape: **81% of plan lines are prose and evidence, 19% trackable
  state.** A task body runs 380–1165 words and carries SES case ids, DNS
  records, DPU figures and contrast ratios. That is a technical record, not a
  ticket description.

### Why the inbox goes — the measurements that decided that

- **The two files were already exempt from every mechanism governing the rest.**
  0 and 3 claims, no fact fences, no line-cap entry, one inbound code reference
  and that a comment. `doc-line-counts.ts` excluded them **by SIZE, never by
  name** — `docLineCounts` filters on `n > LIMIT` and the two filenames appear
  only inside the doc comment explaining why that filter exists. The repository
  had already classified them as a different species, in prose rather than in a
  condition.
- **It was not working as an inbox.** Groomed exactly once in eleven days
  (2026-08-18, 7 → 0) while the idea list grew back to 24. Median "bare bullet"
  191 characters against a rule that says bare bullets. An empty bullet sat
  unnoticed for two days because nothing validates that file.
- **Capture, not storage, was the failing half.** Four ideas were sitting
  UNCOMMITTED in the working tree at the moment this was decided — a line typed
  into a file is not a line that reaches `git`. This is the criterion the owner
  named: filing an idea from a phone without extra movements.

### Why GitHub Issues and not a task manager

Weighed against agiflow.io, which was the alternative on the table.

- **`Closes #N` works here directly, because `dev` is the default branch.** The
  issue closes as a side effect of the squash-merge that D73 already requires,
  and GitHub leaves the commit↔issue link behind. No external tracker offers
  that, and it removes the exact friction the migration was for: 22 of 108 plan
  commits were nothing but a status tick.
- **Zero context cost for an agent.** `gh issue list --json` is a shell call at
  ~100 ms measured, against ~40 ms for a local read. An MCP server keeps tool
  schemas resident in context for every session whether used or not.
- **No lock-in.** GitHub's REST API is documented and `gh issue list --json`
  exports everything. agiflow.io publishes no REST documentation for creating a
  task on either its site or its docs, and its project-management MCP server is
  not among its 13 public repositories — so the data would have had one copy, in
  a hosted store, with no documented way out. Its org has 12 followers.
- **Both apps cost 5–6 taps; neither is "without extra movements".** The
  two-tap path needs an API, and only one of the two has one. The owner chose
  the GitHub app directly over a shortcut: nothing to build, nothing to break.

Privacy was explicitly NOT the criterion. Issues on this repository are public,
which is no change — `USER-BUGS-DRAFT.md` was already world-readable through the
API.

### What carries over unchanged

The rules were never about the file, and they survive it:

- **Never implement from an issue directly**, and **never fix off a `bug` issue
  directly** — a line there is a symptom, not a diagnosis. Reproduce, write the
  failing test, then fix.
- **A pasted sample is BYTES.** Issue #1 carries a U+00A0 as its thousands
  separator, which is plausibly the whole bug. All 27 bodies were verified
  byte-identical to the lines they replaced.
- A missing capability is an `enhancement`, not a `bug`; a cosmetic shipped on
  purpose is `FOLLOW-UPS.md`, which stays in `git` — it is a record of measured
  verifications, 15 of its 16 rows closed, not a backlog.
- **Grooming is the handoff.** An issue becomes work by getting a Status row in
  the right index and its body in the matching section file, in one commit.

### The exclusion that stays although its reason left

`doc-line-counts.ts` excludes any Markdown file at or under 200 lines from the
length baseline, and the comment justifying it names these two files. **The
exclusion stays, and removing it would be the regression.** The leak it closes
is structural — any hand-edited file sitting uncommitted while a regenerator
runs would have its working-tree length pinned as a committed integer — and the
repository is meant to keep accepting such files. The original paragraph is kept
as the record of what first demonstrated the leak, with a note that the example
is now historical. This is stated here because a later reader finding a
justification whose subject no longer exists would otherwise be right to delete
it.

### What this does not decide

- **The visibility of finished work is a separate problem and is not fixed by
  this.** 53 closed tasks live in `docs/archive/` and a reader must open 14
  files plus the ledger to see the state of the project. No tracker addresses
  that, because the plans stay in `git`; a generated board out of the repository
  is the candidate and is not filed as a task yet.
- **The dated gates in `PLAN-WAITING.md` still have nothing watching them**
  (2026-09-02, 2026-09-10, 2026-09-24). A reminder is the candidate, not a
  tracker field.
